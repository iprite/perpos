## 1. ทำไมยังเป็น Stalwart (ตอบคำถาม "มีตัวอื่นแนะนำมั้ย")

ผมเทียบให้ครบแล้ว — **สำหรับโจทย์เฉพาะของคุณ Stalwart ชนะขาด ไม่ต้องเปลี่ยน** เหตุผลคือคุณมี 3 ข้อบังคับ
ที่ตัดตัวเลือกอื่นออกเกือบหมด: (ก) จะเขียน webmail เองด้วย Next.js, (ข) ต้อง provision จากโค้ดได้, (ค) เครื่องเล็กสุด (RAM 1GB)

| ตัวเลือก | RAM ขั้นต่ำ | provision ด้วย API | JMAP (สำหรับ webmail เอง) | multi-tenant | สรุป |
| -------- | ----------- | ------------------ | ------------------------- | ------------ | ---- |
| **Stalwart** ✅ | **~100–150MB idle** | **REST Management API + API key** | **native** | Enterprise (แต่ทำเองที่ชั้นแอปได้) | **เลือกตัวนี้** |
| mailcow | 2GB+ / 15 containers | API มี | ❌ (IMAP อย่างเดียว) | มี domain-admin | **ตกทันที** — ไม่ลงเครื่อง 1GB |
| Maddy | เบา (Go) | ❌ config file | ❌ | ❌ | provision อัตโนมัติไม่ได้ → ตก |
| Mox | เบา (Go) | admin API มี | ❌ | ❌ | ออกแบบมาเพื่อ "โดเมนตัวเอง" ไม่ใช่ขายต่อ → ตก |
| Postfix + Dovecot + Postgres | เบามาก | เขียน SQL เอง | ❌ | ทำเองได้ 100% | ยืดหยุ่นสุด แต่ **ต้องประกอบเองทุกชิ้น** (spam, DKIM, ACME, admin, quota) → งานเพิ่ม 3–4 เท่า |
| Modoboa / iRedMail | 2GB+ | REST มี | ❌ | มี | หนัก + ยังต้องพึ่ง Postfix/Dovecot ข้างใต้ |

**สิ่งที่ทำให้ Stalwart ขาดลอยสำหรับเรา** (ยืนยันจากเอกสารทางการแล้ว):

- **REST Management API + API key principal** → สร้างโดเมน/บัญชี/alias จาก Next.js ได้ตรง ๆ ไม่ต้อง ssh ไปแก้ไฟล์
- **JMAP เป็น protocol พื้นฐาน** → webmail ที่เขียนใน Next.js คุยตรงได้ ไม่ต้องแปลง IMAP (ตัวอื่นไม่มีเลย)
- **automate DNS บน Cloudflare ได้ในตัว** — สร้าง MX / SPF / DKIM / DMARC / TLSA ให้เอง (ตรงกับที่คุณใช้ Cloudflare อยู่แล้ว)
- **auto-DKIM ต่อโดเมน** (สร้าง + หมุนกุญแจเอง) → ไม่ต้องเขียนระบบหมุนคีย์เอง
- **ACME ในตัว** → ใบรับรอง TLS ของ `mail.perpos.ai` ต่ออายุเองอัตโนมัติ
- **relay / smarthost** → ชี้ขาออกเข้า SES ได้ตามแผน
- ไบนารีเดียว Rust · idle ~100MB · **ลงเครื่อง 1GB ได้สบาย** (mailcow กินมากกว่า 15 เท่า)

> **สรุป: ไม่ต้องเปลี่ยน** ตัวเลือกสำรองเดียวที่สมเหตุผลคือ Postfix+Dovecot+Postgres — เลือกเมื่อคุณ *ไม่อยาก
> ผูกกับสัญญาอนุญาตของใครเลย และยอมเขียนเองเยอะ* แต่ตอนนี้ยังไม่จำเป็น (ดูเรื่อง license ด้านล่าง)

### แล้วถ้า "เขียนเมลเซิร์ฟเวอร์เองเลย" ล่ะ? → **ไม่คุ้ม** (มีตัวเลขยืนยัน)

ผมโคลนซอร์ส Stalwart มานับจริง (2026-08-14):

| วัด | ตัวเลขจริง |
| --- | ---------- |
| โค้ด Rust | **410,891 บรรทัด** / 1,117 ไฟล์ |
| แยกเป็น crate | **26 ตัว** (smtp, imap, imap-proto, jmap, jmap-proto, dav, store, spam-filter, nlp, …) |
| **RFC ที่อ้างถึงในโค้ด** | **62 ฉบับ** |
| ระยะเวลาพัฒนา | ~5–6 ปี โดยทีมที่มีนักพัฒนาหลักคนเดียวเป็นแกน |

**ต่อให้ตัดของที่เราไม่ใช้ทิ้งหมด** (CalDAV/CardDAV/WebDAV/POP3/ManageSieve) เหลือแค่แกนที่จำเป็นจริง —
SMTP (19k) + IMAP (21k) + store (24k) + email (9k) + spam-filter (8k) + common (36k) —
ก็ยัง **~117,000 บรรทัดของโค้ดโปรโตคอลที่ต้องถูกต้องเป๊ะ** ประเมินคร่าว ๆ **2–4 ปี-คน**
สำหรับคนที่รู้เรื่องอีเมลลึกอยู่แล้ว

#### 5 อย่างที่ฆ่าโปรเจกต์ "เขียนเมลเซิร์ฟเวอร์เอง" (ไม่ใช่เรื่องเขียนโค้ดไม่เป็น)

1. **Deliverability ไม่ใช่ปัญหาเชิงโค้ด** — Gmail/Outlook รับเมลเราหรือไม่ ขึ้นกับชื่อเสียง + รายละเอียดยิบย่อย
   บั๊กเล็ก ๆ อย่าง DKIM canonicalization ผิด, `Message-ID` ผิดรูป, header เธรดเพี้ยน
   → **เมลเข้าถังสแปมเงียบ ๆ ไม่มี error ให้ debug** นี่คือฝันร้ายจริงของทุกคนที่เคยลอง
2. **IMAP ต้องถูกต้องระดับโหด** — Apple Mail / Outlook ไม่ให้อภัย บั๊กเดียว = กล่องจดหมายพัง เมลซ้ำ หรือ **เมลหาย**
   · เราขายบริการที่ "เมลลูกค้าหาย" = จบธุรกิจ ไม่ใช่แค่บั๊ก
3. **เปิดพอร์ต 25 = แปะ parser ให้คนทั้งอินเทอร์เน็ตยิง** — MIME parser เป็นแหล่ง RCE/DoS คลาสสิก
   เขียนเองคือรับความเสี่ยงความปลอดภัยเต็ม ๆ บนข้อมูลที่อ่อนไหวที่สุดของลูกค้า
4. **มาตรฐานที่ไม่รู้ว่ามีจนโดนเล่นงาน** — DANE, MTA-STS, TLS-RPT, ARC, SRS (ตอน forward), greylisting,
   backscatter, BIMI · 62 RFC ในโค้ด Stalwart ไม่ได้ใส่มาเล่น ๆ
5. **ไม่ใช่โปรเจกต์ แต่เป็นภาระถาวร** — กติกาผู้ส่งเปลี่ยนทุกปี (เช่นกฎ bulk sender ของ Google/Yahoo)
   ต้องมีคนตามตลอดอายุธุรกิจ

#### แล้วอะไรที่ "ควรเขียนเอง" จริง ๆ?

**สิ่งที่คุณวางแผนไว้อยู่แล้วทั้งหมด — และนั่นคือที่ที่มูลค่าอยู่จริง:**

| เขียนเอง ✅ | ใช้ของเขา ❌ ไม่ต้องเขียน |
| ----------- | ------------------------- |
| **webmail UI** (Phase 3, JMAP) | เอนจิน SMTP / IMAP / JMAP |
| **ชั้น provisioning + multi-tenant** (Phase 2) | spam filter, DKIM/DMARC/ARC |
| **ตัวช่วยตั้ง DNS + ตรวจสอบ** | การจัดเก็บ/ดัชนี/ค้นหาเมล |
| **billing + โควตา** ต่อเข้า `usage_events` | ACME / TLS |
| **แจ้งเตือน LINE, ผูกกับ ERP** | คิวส่งออก, retry, bounce parsing |

ลูกค้าไม่ได้จ่ายเงินให้เราเพราะเรามีเอนจิน IMAP ของตัวเอง — จ่ายเพราะ **"อีเมลบริษัทที่ผูกกับระบบบัญชี
และดูแลให้ทั้งหมด"** ซึ่งอยู่ในชั้นที่เราเขียนเองอยู่แล้ว

#### ทางสายกลางที่สมเหตุผล (ถ้าอยากได้ "ของเราเอง")

**fork Stalwart แล้วแก้ตามใจ** — AGPL อนุญาตให้แก้ได้เต็มที่ แค่ต้องเปิดซอร์สส่วนที่แก้
(หรือถือ Enterprise $5/เดือน ก็ไม่ต้องเปิดด้วยซ้ำ) → ได้ควบคุม 100% โดยไม่ต้องเสีย 2–4 ปี-คน

> **สรุป**: ถ้าแรงจูงใจคือ *ค่าไลเซนส์* — มันแค่ $5/เดือน เขียนเองแพงกว่าเป็นพันเท่า ·
> ถ้าคือ *ความยืดหยุ่น* — fork เอาได้เลย · ถ้าคือ *อยากเป็นเจ้าของเทคโนโลยี* — เจ้าของที่แท้จริงคือ
> ชั้นที่ติดกับลูกค้า (webmail + ERP integration) ไม่ใช่ชั้นโปรโตคอลที่เป็นสินค้าโภคภัณฑ์ไปแล้ว

**ถ้าอยากประหยัดสุดจริง ๆ ก็ใช้ Community ได้ ไม่ผิด** — โดเมน/กล่องไม่จำกัดเหมือนกัน แค่ยอมรับว่า
งานซัพพอร์ตจะหนักกว่า และห้ามแตะซอร์สโค้ด Stalwart

## 2.5 ผู้ให้บริการ: DigitalOcean หรือ GCP? → **แนะนำ GCP**

**ข้อสรุป: ย้ายไป GCP ครับ** เหตุผลหลักไม่ใช่ราคา (GCP แพงกว่า ~2 เท่า) แต่เป็น **การกำจัดความเสี่ยง
และการที่คุณลงทุนสร้างระบบติดตามต้นทุน GCP ไว้แล้วทั้งกอง**

### เหตุผลที่ 1 (สำคัญสุด) — **ลบความเสี่ยงอันดับ 1 ของแผนทิ้งทั้งข้อ**

| | DigitalOcean | **GCP (Compute Engine)** |
| - | ------------ | ------------------------ |
| พอร์ต **25** ขาออก | ❌ บล็อก | ❌ บล็อกถาวร ปลดไม่ได้ (นโยบายแพลตฟอร์ม ไม่ใช่ firewall) |
| พอร์ต **465 / 587** ขาออก | ❌ **บล็อกด้วย** | ✅ **ใช้ได้ปกติ** |
| พอร์ต **25 ขาเข้า** (รับเมล/MX) | ✅ ได้ | ✅ ได้ (บล็อกเฉพาะ *ขาออก*) |
| ตั้ง PTR / reverse DNS | ต้องตั้งในแผงควบคุม | ✅ ตั้งได้บน static external IP |

**นี่คือจุดตาย** — บน DO เราต้องพึ่งพอร์ตสำรอง **2587** ของ SES และถ้ามันโดนบล็อกด้วย
ทั้งแผนต้องเปลี่ยนผู้ให้บริการ (Phase 0 go/no-go) · **บน GCP เราต่อ SES ที่พอร์ต 587 มาตรฐานได้เลย
ไม่ต้องลุ้น** → **งาน go/no-go ที่เสี่ยงที่สุดหายไปทั้งข้อ**

> GCP บล็อกพอร์ต 25 ขาออกถาวรจริง แต่ **เราไม่ได้ใช้** เพราะออกทาง SES อยู่แล้ว
> ส่วนขาเข้า (MX รับเมล) ไม่โดนบล็อก ใช้งานได้ปกติ

### เหตุผลที่ 2 — **ต้นทุนจะมองเห็นอัตโนมัติ ไม่เป็นจุดบอด**

AGENTS.md ของคุณเขียนไว้เองว่า **"แอปใหม่ให้ผูกใบ perpos เสมอ"** (บิลใบเดียว = ส่วนลด spending-based
กองเดียว + BigQuery export ชุดเดียวครบทุกแอป) — droplet ที่ DO **ผิดกติกาข้อนี้ตรง ๆ**

- ท่อ `billing_export` → `infra_costs` → `/admin/usage` ที่คุณสร้างไว้ **มองเห็นเฉพาะ GCP**
  → VM บน GCP โผล่ในแท็บโครงสร้างพื้นฐานเองตั้งแต่วันแรก · DO ต้องเขียน sync ใหม่ หรือกลายเป็นค่าใช้จ่ายที่หายไปจากระบบ
- คุณเคยเจ็บมาแล้วกับ `exapp-clip-renderer` ที่กิน **฿886/เดือนโดยไม่มีใครเห็น** — ระบบติดตามต้นทุนทั้งหมด
  เกิดขึ้นเพราะบทเรียนนั้น **การเพิ่มผู้ให้บริการนอกระบบติดตาม = สร้างจุดบอดใหม่ด้วยมือตัวเอง**
- VM ต้องติด label `app=perpos` ตอนสร้าง (กติกาเดิมของคุณ) → แยกบิลถูกอัตโนมัติ

### เหตุผลที่ 3 — ลดผู้ให้บริการ ใช้ของที่ตั้งไว้แล้วซ้ำ

Secret Manager (มี `WORKER_SECRET`/`GEMINI_API_KEY` อยู่แล้ว) · Cloud Monitoring · Cloud Scheduler ·
IAM · snapshot สำรองดิสก์ในตัว — **ไม่ต้องเปิดบัญชี/บัตรเครดิต/ระบบเฝ้าระวังชุดที่สอง**

### 💡 ถ้าย้ายไป GCP → ควรเปลี่ยน blob store จาก R2 เป็น **GCS** ด้วย

นี่เป็นผลพลอยได้ที่สำคัญ — ข้อเสียใหญ่สุดของ R2 (ตาม §3) คือ latency ข้ามเน็ตตอนเปิดอ่านเมล
**ถ้า VM อยู่ GCP `asia-southeast1` แล้วใช้ GCS bucket ที่ region เดียวกัน ข้อเสียนั้นหายไป:**

| | R2 (ข้ามคลาวด์) | **GCS same-region** |
| - | --------------- | ------------------- |
| latency ตอนเปิดเมล | ~50–150 ms | **~1–5 ms** |
| ค่าเก็บ | $0.015/GB | $0.020/GB (ต่างกัน $0.50/เดือน ที่ 100GB) |
| ค่าโอนเข้า VM | ฟรี | **ฟรี (region เดียวกัน)** |
| อยู่ในบิล/ระบบติดตามเดียวกัน | ❌ | ✅ |

→ **แพงกว่าเดือนละไม่ถึง $1 แต่เร็วกว่า 30 เท่า และตัดผู้ให้บริการออกอีกราย**
(ยังใช้ R2 ได้ถ้าอยากประหยัด — แค่ยอม latency)

### ⚠️ สิ่งที่ต้องรู้ก่อนย้าย

1. **ต้องใช้ Compute Engine ไม่ใช่ Cloud Run** — Cloud Run เปิดพอร์ต 25 ฟังไม่ได้, ไม่มี state ถาวร,
   ไม่รองรับ TCP ยาว ๆ · **นี่เป็นโหมดใหม่สำหรับทีม** (ที่ผ่านมาใช้แต่ Cloud Run) = ต้องดูแล VM เอง
   (patch OS, firewall, monitoring) เหมือน DO ทุกประการ ไม่ได้ง่ายกว่า
2. **egress คิดเงิน** — DO แถม 1TB ฟรี, GCP คิดตาม GB (มีโควตาฟรีก้อนหนึ่ง แล้วประมาณ $0.12–0.19/GB ใน APAC)
   → webmail ที่คนใช้เยอะ = egress โต · ตอนนี้ปริมาณยังน้อยไม่กระทบ แต่ **ต้องตั้ง budget alert ไว้**
3. **static external IPv4 คิดเงินแล้ว** (~$3.6/เดือน) ต่างจาก DO ที่ Reserved IP ฟรีเมื่อผูก droplet
4. ราคาแพงกว่า ~2 เท่า — ดูตาราง §8

### ทางเลือกที่ 3: Hetzner (ถ้า "ถูกที่สุด" คือเป้าหมายเดียว)

ไม่บล็อกพอร์ตเมลหลังยืนยันตัวตน · ราคาถูกกว่า DO อีก · IP reputation ดีกว่าทั้งคู่
**แต่**เพิ่มผู้ให้บริการรายที่ 3 และอยู่นอกระบบติดตามต้นทุนเหมือนกัน → **ไม่แนะนำ** เว้นแต่ต้นทุนเป็นข้อจำกัดจริง ๆ

## 3. ⚠️ จุดที่คำตอบคุณ 2 ข้อขัดกัน — ขอเสนอทางออก

คุณเลือก **"NVMe ก่อน + R2 เป็น backup"** และ **"เครื่องเล็กสุด"** — สองข้อนี้อยู่ด้วยกันไม่ได้:

- เครื่องเล็กสุด (DO $6 = 25GB · GCE e2-micro + PD 25GB) หัก OS + RocksDB + log แล้วเหลือให้เมล ~18–20GB
- ถ้าให้ลูกค้ากล่องละ 2GB → **รับได้ ~9–10 กล่องแล้วเต็ม** ขายลูกค้าที่ 3 ก็ตันแล้ว
- ดิสก์เต็มบนเมลเซิร์ฟเวอร์ = **รับเมลไม่ได้ทั้งระบบทุกลูกค้าพร้อมกัน** (ไม่ใช่แค่ช้า) เป็น failure mode ที่แย่ที่สุด
- ขยายดิสก์ = resize เครื่อง (DO) หรือเพิ่ม PD (GCP ~$0.11/GB) — **แพงกว่า object storage 5–7 เท่า**

### ข้อเสนอ (แนะนำ): สลับเป็น **RocksDB บน NVMe + blob ไป object storage ตั้งแต่วันแรก**

> ถ้าไปตาม §2.5 (GCP) → ใช้ **GCS same-region** แทน R2 · latency ~1–5ms และโอนเข้า VM ฟรี

| | ของที่อยู่ NVMe | ของที่อยู่ R2 |
| - | --------------- | ------------- |
| อะไร | metadata, index, flag, folder, บัญชีผู้ใช้ | เนื้อจดหมาย + ไฟล์แนบ |
| โตแค่ไหน | **ช้ามาก** (~50–100MB ต่อ 1,000 กล่อง) | โตตามที่ลูกค้าใช้จริง |
| ต้องเร็วมั้ย | **ต้องเร็ว** (ทุกครั้งที่เปิดกล่อง/list เมล) | เร็วเฉพาะตอนกดเปิดอ่านเมล 1 ฉบับ |

**ได้อะไร**: เครื่องเล็กสุดอยู่ได้จริงระยะยาว · เพิ่มลูกค้าไม่ต้องขยายเครื่อง · ดิสก์เต็มยาก · ค่าเก็บ $0.015/GB
(100GB = ~$1.35/เดือน) · **egress ฟรี** ซึ่งสำคัญมากเพราะ webmail อ่านเมลคือ egress ล้วน ๆ

**เสียอะไร**: กดเปิดอ่านเมลแต่ละฉบับมี latency เพิ่มจากการไป R2 (ประเมิน +50–150ms จาก SGP1)
— **ยอมรับได้** เพราะการ list กล่อง/ค้นหา/เช็คเมลใหม่ (ซึ่งเป็น 90% ของการใช้งาน) ยังอ่านจาก NVMe ทั้งหมด

**ยังได้ backup เหมือนเดิม**: ตั้ง R2 bucket ที่สอง (`perpos-mail-backup`) รับ snapshot ของ RocksDB รายวัน
→ ได้ทั้ง blob store และ backup ตามที่คุณต้องการ แค่คนละ bucket

> ถ้าคุณยังอยากได้ NVMe-first จริง ๆ ทางเดียวคือ **ขยับเป็น droplet $12 (2GB/50GB)** + Block Storage
> ตามจำนวนลูกค้า — ทำได้ แต่ต้นทุนต่อกล่องจะแพงกว่า R2 หลายเท่าและต้องคอยเฝ้าดิสก์เอง
> **ผมแนะนำ R2-first แต่ตัดสินใจสุดท้ายเป็นของคุณ — บอกมาได้ถ้าจะเอาแบบเดิม**

## 4. Phase 0 — งาน go/no-go ต้องทำก่อนจ่ายเงินอะไรทั้งสิ้น

**ห้ามข้าม** — ทำบน **GCP `asia-southeast1`** ตาม §2.5 (ถ้ายืนยันจะใช้ DO ให้เปลี่ยนข้อ 1 เป็นทดสอบพอร์ต 2587)

1. **สร้าง VM + ยืนยันว่าต่อ SES พอร์ต 587 ได้**
   - `gcloud compute instances create perpos-mail --machine-type=e2-micro --zone=asia-southeast1-a`
     **`--labels app=perpos`** ← กติกาเดิมของคุณ ถ้าลืม บิลจะแยกแอปไม่ถูก (label ไม่มีผลย้อนหลัง)
   - `nc -zv email-smtp.ap-southeast-1.amazonaws.com 587` → **ต้องผ่าน** (GCP บล็อกแค่ 25 ขาออก)
   - เช็คว่าพอร์ต 25 **ขาเข้า** ใช้ได้ (เปิด firewall rule แล้วลอง telnet จากข้างนอกเข้ามา)
2. **จอง static external IP + ตั้ง PTR = `mail.perpos.ai`** — ตั้งได้บน primary NIC ของ VM
   · เมลจาก IP ที่ไม่มี PTR ตรงกับชื่อโฮสต์ โดนตีกลับ/เข้าถังสแปมเยอะมาก
3. **ยืนยันว่า blob store ทำงานกับ Stalwart ได้** — สร้าง GCS bucket ที่ `asia-southeast1` (หรือ R2 ถ้ายืนยันใช้ R2)
   → ทดสอบครบวง: ส่งเมลเข้า → อ่านผ่าน IMAP → ลบ → เช็คว่า object หายจริง
4. **ขอปลด SES sandbox** (production access) — ใช้เวลา 24–48 ชม. **ยื่นวันแรกเลย** ไม่งั้นบล็อกงานทีหลัง
   - ตอนยื่นต้องบอกตรง ๆ ว่าเป็น **ISV ส่งแทนลูกค้า** + มีระบบจัดการ bounce/complaint (ไม่งั้นโดนปฏิเสธ)
5. **ตั้ง budget alert บน GCP** — egress กับ VM ที่ลืมปิด คือสองตัวที่บวมเงียบ ๆ (บทเรียน `exapp-clip-renderer`)

### Phase 1 — ตั้งเซิร์ฟเวอร์ + dogfood ด้วยโดเมนตัวเอง
เป้า: **เราใช้เองก่อนขาย** — `iprite@perpos.ai` ใช้งานจริงบน Stalwart

- ติดตั้ง Stalwart (ไบนารี + systemd) · เปิด swap 2GB (droplet 1GB ไม่มี swap มาให้)
- data store = RocksDB บน NVMe · blob store = R2 · ACME ออกใบรับรอง `mail.perpos.ai`
- ตั้ง relay ขาออก → SES `:587` (บน GCP) หรือ `:2587` (ถ้าใช้ DO) · SMTP credentials เก็บใน Secret ไม่ใช่ไฟล์ config ที่ commit)
- ตั้ง DNS ของ `perpos.ai`: MX, SPF (`include:amazonses.com`), DKIM, DMARC (`p=none` ก่อน แล้วค่อยขยับ)
- ไฟร์วอลล์: เปิดเฉพาะ 25 (เข้า), 465/587 (submission เข้า), 993 (IMAP), 443 (JMAP+admin), 22
- **เกณฑ์ผ่าน**: ส่ง–รับกับ Gmail/Outlook ได้ · [mail-tester.com](https://www.mail-tester.com) ได้ **≥ 9/10**

### Phase 2 — โมดูล `mail` ใน PERPOS (โครง + provisioning)

**โมดูลใหม่** ใน [`lib/modules.ts`](apps/perpos/src/lib/modules.ts) — เป็น **shared** (ไม่ใส่ `forOrgSlugs`)
เพราะขายลูกค้าทั่วไป ต่างจาก `acc_firm`/`gov_procure` ที่ล็อก org เดียว

```ts
{
  key: "mail",
  label: "อีเมลบริษัท",
  href: "/mail",
  specific: true,
  match: (p) => { const s = p.split("/").filter(Boolean); return s.length >= 2 && s[1] === "mail"; },
  roles: [
    { key: "owner",  label: "ผู้ดูแลระบบเมล", canWrite: true },   // เพิ่ม/ลบกล่อง, ผูกโดเมน
    { key: "member", label: "ผู้ใช้",         canWrite: true },   // ใช้กล่องตัวเอง
    { key: "viewer", label: "ผู้ดูข้อมูล",     canWrite: false },
  ],
}
```

**ตาราง (migration `supabase/migrations/`)** — RLS ทุกตัวตาม convention:

| ตาราง | เก็บอะไร |
| ----- | -------- |
| `mail_domains` | โดเมนของแต่ละ org + สถานะยืนยัน (`pending`/`verified`/`failed`) + เวลาตรวจล่าสุด |
| `mail_dns_records` | record ที่ลูกค้าต้องไปตั้ง (type/host/value/ตรวจผ่านแล้วหรือยัง) — ทำหน้า "ตัวช่วยตั้ง DNS" |

**ข้อผูกพันที่ห้ามพัง (invariant):**

1. **รหัสผ่านกล่องเมลไม่เก็บใน Supabase เด็ดขาด** — Stalwart hash เอง เราเก็บแค่ metadata

## 6. DNS ที่ลูกค้าแต่ละรายต้องตั้ง

หน้า "ตัวช่วยตั้ง DNS" ต้องปั่น record ชุดนี้ + **ปุ่มตรวจสอบว่าตั้งถูกยัง** (ห้ามให้ลูกค้าเดาเอง)

| Type | Host | Value | ทำไม |
| ---- | ---- | ----- | ---- |
| MX | `@` | `mail.perpos.ai` (priority 10) | รับเมลเข้า |
| TXT | `@` | `v=spf1 include:amazonses.com ~all` | ขาออกผ่าน SES |
| CNAME ×3 | `xxx._domainkey` | (SES Easy DKIM) | DKIM ให้ตรง DMARC |
| TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:dmarc@perpos.ai` | เริ่มที่ `p=none` เก็บสถิติ 2–4 สัปดาห์ ค่อยขยับ `quarantine` |
| CNAME | `autodiscover` | `mail.perpos.ai` | Outlook ตั้งค่าเอง |
| SRV | `_autodiscover._tcp` | `mail.perpos.ai:443` | Outlook |
| CNAME | `autoconfig` | `mail.perpos.ai` | Thunderbird / Apple Mail |

> **ห้ามให้กล่องเมลใช้งานได้ก่อน DNS ผ่านครบ** — ปล่อยผ่านแล้วลูกค้าจะส่งเมลออกไปเข้าถังสแปม
> แล้วโทษเรา งานซัพพอร์ตจะท่วม

## 7. กฎหมาย / PDPA — เรื่องที่ต้องทำ ไม่ใช่ทางเลือก

- **เนื้อหาอีเมลของลูกค้า = ข้อมูลส่วนบุคคลที่อ่อนไหวที่สุดเท่าที่ PERPOS เคยเก็บ** — หนักกว่าเอกสารบัญชี
- ต้องอัปเดต [นโยบายความเป็นส่วนตัว](apps/landing-astro/src/lib/legal.ts): เก็บอะไร, เก็บที่ไหน
  (DO สิงคโปร์ + Cloudflare R2), เก็บนานแค่ไหน, ลบอย่างไรเมื่อเลิกใช้
- ต้องมี **ข้อตกลงประมวลผลข้อมูล (DPA)** กับลูกค้าแต่ละราย — เราเป็น "ผู้ประมวลผล" ลูกค้าเป็น "ผู้ควบคุม"
- **ผู้ดูแลระบบ (รวมเราเอง) ต้องอ่านเมลลูกค้าไม่ได้** — ออกแบบให้ admin เห็นแค่ metadata
  ถ้าจำเป็นต้องเข้าถึงเพื่อแก้ปัญหา ต้องมี audit log + ลูกค้ายินยอมเป็นครั้ง ๆ
- ⚠️ **ห้ามส่งเนื้อหาเมลเข้า AI ทุกกรณีจนกว่าจะแก้นโยบายก่อน** — AGENTS.md ระบุว่าเรารับรองกับ Google
  ไว้เรื่อง Limited Use ถ้าจะทำ "AI สรุปเมล" ต้องอัปเดตนโยบาย §7 และแจ้ง Google **ก่อน** เขียนโค้ด

   (เมลเซิร์ฟเวอร์รัน 24/7 ตลอดอายุธุรกิจอยู่แล้ว ไม่มีเหตุให้จ่ายราคา on-demand)
   · แต่ **อย่าเพิ่งซื้อจนกว่า Phase 0 จะผ่าน** — CUD ผูก 1 ปี ยกเลิกไม่ได้
2. **egress คือตัวที่โตเร็วสุดและมองไม่เห็น** — ที่ 125 กล่องมันแซงค่าเครื่องไปแล้ว ($12 > $7)
   → **ตั้ง budget alert ตั้งแต่วันแรก** · ถ้าโตจนเจ็บ มีทางลด: Standard Tier ($0.085/GB) หรือ
   บีบรูป/แคชฝั่ง client · **ห้ามปล่อยให้โตเงียบ ๆ** (บทเรียน `exapp-clip-renderer`)
3. **`e2-micro` = 1GB / 0.25 vCPU baseline** — พอสำหรับ <25 กล่องแน่นอน (Stalwart idle ~150MB)
   แต่ถ้า TLS handshake + จัดทำดัชนีค้นหาชนกันบ่อย อาจโดน throttle → **`e2-small` (2GB, +$7)
   คือตัวที่ปลอดภัยกว่า** · เริ่ม `e2-micro` แล้วดูกราฟ CPU 2 สัปดาห์ ค่อยตัดสินใจ (resize ได้ ไม่ต้องย้ายข้อมูล)

## 8.5 สำรวจ "ถูกสุด" จากทุกเจ้า (สำรวจ 2026-08-14)

มี 2 กลยุทธ์ที่ต่างกันคนละโลก — **รันเอง** กับ **ไม่รันเลย (เป็นนายหน้า)**

### กลยุทธ์ A — รัน Stalwart เอง: เทียบ VPS ทุกเจ้า (ที่ 5 กล่อง)

| เจ้า | สิงคโปร์ | สเปก | พอร์ต 587 ขาออก | traffic | **฿/เดือน รวมทุกอย่าง** |
| ---- | -------- | ---- | ---------------- | ------- | ----------------------- |
| **Oracle Always Free** | ✅ | 4 ARM / 24GB / 200GB | ✅ (25 ขาออกบล็อก — ไม่ใช้อยู่แล้ว) | 10TB | **≈ ฿5** ⚠️ |
| **Hetzner CPX11** | ✅ | 2 vCPU AMD / 2GB / 40GB | ✅ **ไม่บล็อก** | **20TB รวมแล้ว** | **≈ ฿181** |
| Vultr / Linode | ✅ | 1 vCPU / 1GB | ⚠️ บล็อก 25 ต้องขอปลด | 1–2TB | ≈ ฿200 |
| **GCP e2-micro** (แผนปัจจุบัน) | ✅ | 0.25 vCPU / 1GB | ✅ | **คิดตาม GB** | **≈ ฿435** |
| DigitalOcean | ✅ | 1 vCPU / 1GB | ❌ **บล็อก** | 1TB | ≈ ฿240 (แต่ใช้ไม่ได้) |

> Hetzner CX/CAX (ARM ราคาถูกสุด) **มีเฉพาะยุโรป** — ที่สิงคโปร์ต้องใช้ซีรีส์ **CPX** (AMD)

**Hetzner สิงคโปร์ถูกกว่า GCP 58%** และที่สำคัญกว่าราคา — **traffic 20TB รวมในราคาแล้ว**
ซึ่ง **ลบความเสี่ยง egress ที่เป็นข้อกังวลอันดับ 2 ของแผน GCP ทิ้งทั้งข้อ**
(บน GCP ที่ 125 กล่อง ค่า egress $12 แซงค่าเครื่อง $7 ไปแล้ว — บน Hetzner คือ $0)
· ดิสก์ 40GB ที่แถมมา **พอสำหรับ 5–25 กล่องโดยไม่ต้องใช้ object storage เลย** (ตัด GCS ออกได้อีก)

⚠️ **Oracle Always Free ถูกจริง (แทบ $0) แต่ห้ามเอาข้อมูลลูกค้าจริงไปไว้** —
ไม่มี SLA · Oracle เรียกคืนเครื่อง Always Free ที่ "ไม่ค่อยใช้งาน" ได้ · ARM ที่สิงคโปร์
มักติด "out of host capacity" · **เหมาะเป็นเครื่องหัดตั้ง Stalwart หรือทำ backup MX ตัวที่สอง เท่านั้น**

### กลยุทธ์ B — ไม่รันเซิร์ฟเวอร์เลย ซื้อของเจ้าอื่นมาขายต่อ

| เจ้า | ราคา | ได้อะไร | **฿/เดือน** |
| ---- | ---- | ------- | ----------- |
| **Purelymail** | **$10/ปี** | ไม่จำกัดผู้ใช้/โดเมน/พื้นที่ (ภายใต้ fair use) | **≈ ฿28** |
| **Migadu Micro** | $19/ปี | โดเมน/กล่องไม่จำกัด · จำกัด 200 ส่ง/2,000 รับ ต่อวัน · 5GB | ≈ ฿53 |
| **MXroute** | $59/ปี | โดเมน/บัญชีไม่จำกัด · 10GB · **เปิดกว้างกับนายหน้า** | ≈ ฿165 |
| Zoho Mail Lite | $1/user/เดือน | 5GB/คน | ฿34 × 5 = ฿170 |

**ถูกกว่ารันเองสิบเท่า** — แต่**เปลี่ยนโมเดลธุรกิจ** จาก "เจ้าของบริการ" เป็น "นายหน้า" และมี 5 ข้อเสียที่ต้องรู้:

1. **ไม่มี JMAP** → webmail ที่จะเขียนใน Next.js ต้องต่อ IMAP แทน (ต้องมี bridge IMAP→HTTP วางบน Cloud Run)
2. **ไม่มี isolation จริง** → ลูกค้าทุกรายอยู่บัญชีเดียวกัน · **ลูกค้ารายหนึ่งส่งสแปม = ทุกรายโดนหางเลข** และเราแก้ไม่ได้
3. **ชื่อเสียง IP เป็นของเขา ไม่ใช่ของเรา** — เขาโดน blacklist เมื่อไหร่ ลูกค้าเราเดือดร้อนทันทีและเราทำอะไรไม่ได้เลย
4. **fair use ≠ ใบอนุญาตทำธุรกิจ** — Purelymail "$10 ไม่จำกัด" ตั้งอยู่บนการใช้แบบส่วนตัว
   เอาไปขายต่อเชิงพาณิชย์เสี่ยงโดนคิดเพิ่ม/ปิดบัญชี · **ถ้าจะใช้ทางนี้ให้เลือก MXroute ที่ประกาศชัดว่ารับนายหน้า**
5. **ไม่มี moat** — ลูกค้าไปซื้อตรงกับเขาเองได้ ราคาถูกกว่าเราอีก

### 📊 สรุปให้เลือก

| ทาง | ฿/เดือน (5 กล่อง) | เลือกเมื่อ |
| --- | ------------------ | ---------- |

**หรือ**เขียน sync เพิ่ม · ส่วนข้อ 1 (ความเสี่ยงพอร์ต) **Hetzner ไม่มีปัญหา** — 587 เปิดอยู่แล้ว
และขอปลด 25 ได้หลังจ่ายบิลเดือนแรก

> **ความเห็นผม**: ถ้า "ถูกสุด" คือเป้าหมายจริง → **Hetzner CPX11 สิงคโปร์** คือคำตอบ
