## 0. สรุปสำหรับคนรีบ

**แผนเดิมที่คุณร่างมาใช้ได้จริง และเลือกของถูกตัวเกือบทั้งหมด** — Stalwart, R2, SES เป็นชุดที่เข้ากันดี
แต่มี **4 เรื่องที่ต้องรู้ก่อนจ่ายเงิน** ไม่งั้นจะไปตายกลางทาง:

| # | เรื่อง | ผลกระทบ |
| - | ------ | -------- |
| 1 | **ผู้ให้บริการบล็อกพอร์ตขาออก** | DO บล็อก 25/465/587 (ใช้ไม่ได้) · GCP บล็อก 25 ถาวร · **เคาะแล้ว: Hetzner สิงคโปร์** — 587 เปิดอยู่แล้ว, 25 ขอปลดได้หลังจ่ายบิลเดือนแรก, traffic 20TB รวมในราคา → **ความเสี่ยงนี้หายไปทั้งข้อ** ดู §2.5 |
| 2 | **multi-tenancy ของ Stalwart เป็นฟีเจอร์ Enterprise** | แต่**ตัวฟรีไม่จำกัดจำนวนกล่อง/โดเมนเลย** (ดู §1) · และ Enterprise ซื้อผ่าน GitHub Sponsors ได้ที่ **$5/เดือน (25 กล่อง)** → **แนะนำจ่าย** เพราะได้ประวัติการส่งเมล + กู้คืนเมลที่ลบ ซึ่งจำเป็นกับบริการที่เก็บเงิน |
| 3 | **R2 เก็บได้แค่ "ตัวจดหมาย" (blob) ไม่ใช่ metadata** | Stalwart ต้องมี 2 ชั้นเสมอ: *data store* (index/flag/folder) + *blob store* (เนื้อเมล) → R2 แทนได้แค่ชั้นหลัง |
| 4 | **ดิสก์เต็ม = รับเมลไม่ได้ทั้งระบบ** | Hetzner `cpx11` แถมดิสก์ 40GB → **พอถึง ~25 กล่องโดยไม่ต้องใช้ object storage** · เกินกว่านั้นค่อยเพิ่ม Volume หรือย้าย blob ออก ดู §3 |

**ตัดสินใจแล้ว: Hetzner Cloud `sin-dc1` (สิงคโปร์) + Stalwart Community + AWS SES**
**ช่วง pilot 5 กล่อง ≈ ฿190–240/เดือน** — โครงสร้างพื้นฐานเป็นโค้ดแล้วที่ [`infra/mail/`](infra/mail/) · ดู §8

## 1. ทำไมยังเป็น Stalwart (ตอบคำถาม "มีตัวอื่นแนะนำมั้ย")

ผมเทียบให้ครบแล้ว — **สำหรับโจทย์เฉพาะของคุณ Stalwart ชนะขาด ไม่ต้องเปลี่ยน** เหตุผลคือคุณมี 3 ข้อบังคับ
ที่ตัดตัวเลือกอื่นออกเกือบหมด: (ก) จะเขียน webmail เองด้วย Next.js, (ข) ต้อง provision จากโค้ดได้, (ค) เครื่องเล็กสุด (RAM 1GB)

| ตัวเลือก | RAM ขั้นต่ำ | provision ด้วย API | JMAP (สำหรับ webmail เอง) | multi-tenant | สรุป |
| -------- | ----------- | ------------------ | ------------------------- | ------------ | ---- |
| **Stalwart** ✅ | **~100–150MB idle** | **REST Management API + API key** | **native** | Enterprise (แต่ทำเองที่ชั้นแอปได้) | **เลือกตัวนี้** |
| mailcow | 2GB+ / 15 containers | API มี | ❌ (IMAP อย่างเดียว) | มี domain-admin | **ตกทันที** — ไม่ลงเครื่อง 1GB |
| Maddy | เบา (Go) | ❌ config file | ❌ | ❌ | provision อัตโนมัติไม่ได้ → ตก |
| Mox | เบา (Go) | admin API มี | ❌ | ❌ | ออกแบบมาเพื่อ "โดเมนตัวเอง" ไม่ใช่ขายต่อ → ตก |
| Postfix + Dovecot + Postgres | เบามาก | เขียน SQL เอง | ❌ | ทำเองได้ 100% | ยืดหยุ่นสุด แต่ **ต้องประกอบเองทุกชิ้น** (spam, DKIM, ACME, admin, quota) → งานเพิ่ม 3–4 เท่า |
| Modoboa / iRedMail | 2GB+ | REST มี | ❌ | มี | หนัก + ยังต้องพึ่ง Postfix/Dovecot ข้างใต้ |

**สิ่งที่ทำให้ Stalwart ขาดลอยสำหรับเรา** (ยืนยันจากเอกสารทางการแล้ว):

- **REST Management API + API key principal** → สร้างโดเมน/บัญชี/alias จาก Next.js ได้ตรง ๆ ไม่ต้อง ssh ไปแก้ไฟล์
- **JMAP เป็น protocol พื้นฐาน** → webmail ที่เขียนใน Next.js คุยตรงได้ ไม่ต้องแปลง IMAP (ตัวอื่นไม่มีเลย)
- **automate DNS บน Cloudflare ได้ในตัว** — สร้าง MX / SPF / DKIM / DMARC / TLSA ให้เอง (ตรงกับที่คุณใช้ Cloudflare อยู่แล้ว)
- **auto-DKIM ต่อโดเมน** (สร้าง + หมุนกุญแจเอง) → ไม่ต้องเขียนระบบหมุนคีย์เอง
- **ACME ในตัว** → ใบรับรอง TLS ของ `mail.perpos.ai` ต่ออายุเองอัตโนมัติ
- **relay / smarthost** → ชี้ขาออกเข้า SES ได้ตามแผน
- ไบนารีเดียว Rust · idle ~100MB · **ลงเครื่อง 1GB ได้สบาย** (mailcow กินมากกว่า 15 เท่า)

> **สรุป: ไม่ต้องเปลี่ยน** ตัวเลือกสำรองเดียวที่สมเหตุผลคือ Postfix+Dovecot+Postgres — เลือกเมื่อคุณ *ไม่อยาก
> ผูกกับสัญญาอนุญาตของใครเลย และยอมเขียนเองเยอะ* แต่ตอนนี้ยังไม่จำเป็น (ดูเรื่อง license ด้านล่าง)

### แล้วถ้า "เขียนเมลเซิร์ฟเวอร์เองเลย" ล่ะ? → **ไม่คุ้ม** (มีตัวเลขยืนยัน)

ผมโคลนซอร์ส Stalwart มานับจริง (2026-08-14):

| วัด | ตัวเลขจริง |
| --- | ---------- |
| โค้ด Rust | **410,891 บรรทัด** / 1,117 ไฟล์ |
| แยกเป็น crate | **26 ตัว** (smtp, imap, imap-proto, jmap, jmap-proto, dav, store, spam-filter, nlp, …) |
| **RFC ที่อ้างถึงในโค้ด** | **62 ฉบับ** |
| ระยะเวลาพัฒนา | ~5–6 ปี โดยทีมที่มีนักพัฒนาหลักคนเดียวเป็นแกน |

**ต่อให้ตัดของที่เราไม่ใช้ทิ้งหมด** (CalDAV/CardDAV/WebDAV/POP3/ManageSieve) เหลือแค่แกนที่จำเป็นจริง —
SMTP (19k) + IMAP (21k) + store (24k) + email (9k) + spam-filter (8k) + common (36k) —
ก็ยัง **~117,000 บรรทัดของโค้ดโปรโตคอลที่ต้องถูกต้องเป๊ะ** ประเมินคร่าว ๆ **2–4 ปี-คน**
สำหรับคนที่รู้เรื่องอีเมลลึกอยู่แล้ว

#### 5 อย่างที่ฆ่าโปรเจกต์ "เขียนเมลเซิร์ฟเวอร์เอง" (ไม่ใช่เรื่องเขียนโค้ดไม่เป็น)

1. **Deliverability ไม่ใช่ปัญหาเชิงโค้ด** — Gmail/Outlook รับเมลเราหรือไม่ ขึ้นกับชื่อเสียง + รายละเอียดยิบย่อย
   บั๊กเล็ก ๆ อย่าง DKIM canonicalization ผิด, `Message-ID` ผิดรูป, header เธรดเพี้ยน
   → **เมลเข้าถังสแปมเงียบ ๆ ไม่มี error ให้ debug** นี่คือฝันร้ายจริงของทุกคนที่เคยลอง
2. **IMAP ต้องถูกต้องระดับโหด** — Apple Mail / Outlook ไม่ให้อภัย บั๊กเดียว = กล่องจดหมายพัง เมลซ้ำ หรือ **เมลหาย**
   · เราขายบริการที่ "เมลลูกค้าหาย" = จบธุรกิจ ไม่ใช่แค่บั๊ก
3. **เปิดพอร์ต 25 = แปะ parser ให้คนทั้งอินเทอร์เน็ตยิง** — MIME parser เป็นแหล่ง RCE/DoS คลาสสิก
   เขียนเองคือรับความเสี่ยงความปลอดภัยเต็ม ๆ บนข้อมูลที่อ่อนไหวที่สุดของลูกค้า
4. **มาตรฐานที่ไม่รู้ว่ามีจนโดนเล่นงาน** — DANE, MTA-STS, TLS-RPT, ARC, SRS (ตอน forward), greylisting,
   backscatter, BIMI · 62 RFC ในโค้ด Stalwart ไม่ได้ใส่มาเล่น ๆ
5. **ไม่ใช่โปรเจกต์ แต่เป็นภาระถาวร** — กติกาผู้ส่งเปลี่ยนทุกปี (เช่นกฎ bulk sender ของ Google/Yahoo)
   ต้องมีคนตามตลอดอายุธุรกิจ

#### แล้วอะไรที่ "ควรเขียนเอง" จริง ๆ?

**สิ่งที่คุณวางแผนไว้อยู่แล้วทั้งหมด — และนั่นคือที่ที่มูลค่าอยู่จริง:**

| เขียนเอง ✅ | ใช้ของเขา ❌ ไม่ต้องเขียน |
| ----------- | ------------------------- |
| **webmail UI** (Phase 3, JMAP) | เอนจิน SMTP / IMAP / JMAP |
| **ชั้น provisioning + multi-tenant** (Phase 2) | spam filter, DKIM/DMARC/ARC |
| **ตัวช่วยตั้ง DNS + ตรวจสอบ** | การจัดเก็บ/ดัชนี/ค้นหาเมล |
| **billing + โควตา** ต่อเข้า `usage_events` | ACME / TLS |
| **แจ้งเตือน LINE, ผูกกับ ERP** | คิวส่งออก, retry, bounce parsing |

ลูกค้าไม่ได้จ่ายเงินให้เราเพราะเรามีเอนจิน IMAP ของตัวเอง — จ่ายเพราะ **"อีเมลบริษัทที่ผูกกับระบบบัญชี
และดูแลให้ทั้งหมด"** ซึ่งอยู่ในชั้นที่เราเขียนเองอยู่แล้ว

#### ทางสายกลางที่สมเหตุผล (ถ้าอยากได้ "ของเราเอง")

**fork Stalwart แล้วแก้ตามใจ** — AGPL อนุญาตให้แก้ได้เต็มที่ แค่ต้องเปิดซอร์สส่วนที่แก้
(หรือถือ Enterprise $5/เดือน ก็ไม่ต้องเปิดด้วยซ้ำ) → ได้ควบคุม 100% โดยไม่ต้องเสีย 2–4 ปี-คน

> **สรุป**: ถ้าแรงจูงใจคือ *ค่าไลเซนส์* — มันแค่ $5/เดือน เขียนเองแพงกว่าเป็นพันเท่า ·
> ถ้าคือ *ความยืดหยุ่น* — fork เอาได้เลย · ถ้าคือ *อยากเป็นเจ้าของเทคโนโลยี* — เจ้าของที่แท้จริงคือ
> ชั้นที่ติดกับลูกค้า (webmail + ERP integration) ไม่ใช่ชั้นโปรโตคอลที่เป็นสินค้าโภคภัณฑ์ไปแล้ว

2. **traffic 20TB รวมในราคา** — ลบความเสี่ยง egress ที่เป็นข้อกังวลอันดับ 2 ของแผน GCP ทิ้งทั้งข้อ
   (บน GCP ที่ 125 กล่อง ค่า egress $12 แซงค่าเครื่อง $7 · บน Hetzner = $0)
3. **ดิสก์ 40GB + Volume ราคาถูก** (~€0.044/GB) — ขยายที่เก็บเมลได้โดยไม่ต้องขยายทั้งเครื่อง

- ค่าเครื่อง**ไม่โผล่ใน `/admin/usage` เอง** — ท่อ `billing_export` เห็นเฉพาะ GCP

## 3. ที่เก็บเมล — ⚠️ **ตัวเลขที่เคยเขียนไว้ผิด แก้แล้ว**

### ความจริงเรื่องดิสก์ 40GB

เดิมเอกสารนี้เขียนว่า "40GB พอถึง ~25 กล่อง" — **คำนวณผิดอย่างมีนัยสำคัญ** ตัวเลขจริง:

```
ดิสก์ cpx11                    40 GB
− OS + Stalwart + log            ~4 GB
− RocksDB (index/metadata)       ~1 GB
− ที่ว่างสำรอง (ห้ามให้เต็ม)      ~5 GB
                              ─────────
เหลือให้เนื้อเมลจริง            ~30 GB
```

### ✅ เคาะแล้ว: **โควตาเริ่มต้น 1GB/กล่อง · ปรับเพิ่มรายกล่องได้**

| โควตา/กล่อง | รับได้บนดิสก์ 40GB | หมายเหตุ |
| ----------- | ------------------- | -------- |
| **1 GB (ค่าเริ่มต้นที่เลือก)** | **~30 กล่อง** | ดิสก์เครื่องพอถึง pilot + ลูกค้า 2–3 รายแรก |
| 5 GB | ~6 กล่อง | ต้องเพิ่ม Volume ทันที |

**ผลดี:** ดิสก์ 40GB ที่แถมมา **พอถึง ~30 กล่องโดยไม่ต้องเสียค่า Volume เลย**
→ ต้นทุนช่วงแรกต่ำกว่าที่ประเมินไว้รอบก่อนมาก (ดู §8)

### ⚠️ 1GB ยังเล็กเมื่อเทียบตลาด — ต้องวางแผนรับมือ

> ~~ข้อขัดแย้งกับการย้ายเมลเก่า~~ **หายไปแล้ว** เพราะตัดสินใจไม่ให้บริการย้ายเมล (§5.2)
> → กล่องเริ่มจากศูนย์ทุกใบ 1GB จึงเป็นขนาดที่สมเหตุผล

Google Workspace ให้ 30GB · ผู้ใช้ธุรกิจที่รับไฟล์แนบทุกวันจะเต็มภายใน **~1–2 ปี**
→ จะมีเคส "กล่องเต็ม" เข้ามาเรื่อย ๆ ซึ่งกับทีมเล็กที่ไม่มี SLA คือภาระที่ไม่อยากได้

**ทางรับมือ (ต้องมีตั้งแต่ M0):**

- เตือนอัตโนมัติที่ **80% และ 95%** ทางอีเมล + ในหน้าเว็บ **ก่อน**เต็ม
- **กล่องเต็มต้องไม่ทำให้เมลหาย** — Stalwart ต้องตอบ `452 mailbox full` (ผู้ส่งจะ retry ~4 วัน)
  **ห้ามตอบ `550`** ซึ่งเป็นการปฏิเสธถาวร = เมลนั้นหายจริง
- หน้าจัดการให้ **ผู้ดูแลของลูกค้าเพิ่มโควตาเองได้ทันที** ไม่ต้องรอเรา (ลดงานซัพพอร์ต)
- ตั้งราคาพื้นที่เพิ่มให้ชัดตั้งแต่แรก (เช่น +฿20/GB/เดือน — ต้นทุนจริง ~฿1.5/GB)
  **นี่เป็นช่องทางรายได้ที่ดี ไม่ใช่แค่ต้นทุน**

### หลักการที่ยังใช้อยู่ (ไม่เปลี่ยน)

Stalwart ต้องมี **2 ชั้นเสมอ** — แยกให้ถูกเวลาย้าย:

| | data store (RocksDB) | blob store |
| - | -------------------- | ---------- |
| เก็บอะไร | index / flag / โฟลเดอร์ / บัญชี | เนื้อจดหมาย + ไฟล์แนบ |
| โตแค่ไหน | **ช้ามาก** (~50–100MB ต่อ 1,000 กล่อง) | โตตามลูกค้าใช้จริง |
| ต้องเร็วไหม | **ต้องเร็ว** — อ่านทุกครั้งที่เปิดกล่อง/list/ค้นหา | เร็วเฉพาะตอนกดเปิดอ่าน 1 ฉบับ |
| **ย้ายออกได้ไหม** | **ห้ามย้ายไป object storage** | ✅ ย้ายได้ (Volume → S3) |

> **ดิสก์เต็ม = รับเมลไม่ได้ทั้งระบบทุกลูกค้าพร้อมกัน** (ไม่ใช่แค่ช้า) — เป็น failure mode ที่แย่ที่สุด
> ของบริการนี้ → **ต้องเตือนที่ 70% ไม่ใช่ 80%** และ Volume ขยายได้โดยไม่ต้องดับเครื่อง

## 4. ลำดับงาน (Phase 0–6)

### Phase 0 — go/no-go ต้องทำก่อนจ่ายเงินอะไรทั้งสิ้น

**ห้ามข้าม** — ทำบน **Hetzner `sin-dc1`** · โครงสร้างพื้นฐานเป็นโค้ดแล้วที่ [`infra/mail/`](infra/mail/)

1. **สร้างเครื่องด้วย Terraform**
   ```bash
   cd infra/mail
   cp terraform.tfvars.example terraform.tfvars   # ใส่ hcloud_token + ssh_public_key
   terraform init && terraform plan               # อ่าน plan ให้ครบก่อน apply
   terraform apply
   ```
   ได้ครบในรอบเดียว: เครื่อง `cpx11` + IPv4/IPv6 คงที่ + firewall (25/465/587/993/443/80) +
   **PTR = `mail.perpos.ai`** + backup อัตโนมัติ
2. **ตั้ง DNS ที่ Cloudflare** — `A` + `AAAA` ของ `mail.perpos.ai` ชี้มาที่ IP ที่ได้จาก `terraform output`
   · ⚠️ **ต้องเป็น DNS only (เมฆเทา)** — Cloudflare ไม่พร็อกซี SMTP/IMAP เปิดเมฆส้มแล้วเมลเข้าไม่ได้
3. **ยืนยันว่าต่อ SES พอร์ต 587 ได้** (จุดที่เคยเป็น go/no-go บน DO — บน Hetzner ควรผ่านสบาย)
   ```bash
   ssh root@<ipv4>
   nc -zv email-smtp.ap-southeast-1.amazonaws.com 587   # ต้องผ่าน
   dig -x <ipv4> +short                                  # ต้องได้ mail.perpos.ai
   ```
4. **ติดตั้ง Stalwart** — `bash /root/install-stalwart.sh` (cloud-init เตรียมไว้ให้แล้ว)
   · ที่เก็บข้อมูล = **RocksDB บนดิสก์เครื่อง** (40GB พอถึง ~25 กล่อง ยังไม่ต้องใช้ object storage)
   · **รหัสผ่านแอดมินโชว์ครั้งเดียว** — เก็บลง password manager ทันที
5. **ขอปลดพอร์ต 25 ขาออกกับ Hetzner** — เปิด limit request ได้**หลังจ่ายบิลเดือนแรก**
   · ยังไม่จำเป็นตอนนี้ (ออกทาง SES อยู่แล้ว) แต่ขอไว้เป็นทางหนีทีไล่ถ้า SES มีปัญหา
6. **ขอปลด SES sandbox** (production access) — 24–48 ชม. **ยื่นวันแรกเลย**
   · ต้องบอกตรง ๆ ว่าเป็น **ISV ส่งแทนลูกค้า** + มีระบบจัดการ bounce/complaint ไม่งั้นโดนปฏิเสธ
7. **บันทึกค่าเครื่องลง `infra_costs`** — Hetzner อยู่นอกท่อ `billing_export` ต้องกรอกเอง
   (ตั้งเตือนรายเดือน ไม่งั้นกลายเป็นต้นทุนที่มองไม่เห็น)

**เกณฑ์ผ่าน Phase 0**: ข้อ 3 ผ่านทั้งสองคำสั่ง + Stalwart ตอบที่ `https://mail.perpos.ai` ได้

### Phase 1 — ตั้งค่า Stalwart + dogfood ด้วยโดเมนตัวเอง
เป้า: **เราใช้เองก่อนขาย** — `iprite@perpos.ai` ใช้งานจริงบน Stalwart อย่างน้อย 2 สัปดาห์

*(เครื่อง/firewall/PTR/swap เสร็จไปแล้วใน Phase 0 ผ่าน Terraform + cloud-init — Phase นี้คือตั้งค่าตัว Stalwart)*

- **relay ขาออก → SES `:587`** · SMTP credentials เก็บใน config ที่ `chmod 600` **ห้าม commit**
- **ACME** ออกใบรับรอง `mail.perpos.ai` (Stalwart ทำเอง) — ตรวจว่าต่ออายุอัตโนมัติจริง
- **DNS ของ `perpos.ai`**: MX · SPF `include:amazonses.com` · DKIM · DMARC **เริ่มที่ `p=none`**
  เก็บสถิติ 2–4 สัปดาห์ค่อยขยับเป็น `quarantine`
- **ตัดสินใจเรื่อง DKIM ให้จบที่ Phase นี้** — ใครเป็นคนเซ็น Stalwart หรือ SES? (ดู §5 ข้อ 3)
- **เปิด Google Postmaster Tools** ของโดเมนตัวเอง → เห็นชื่อเสียง IP/โดเมนตั้งแต่วันแรก
- ตั้ง **fail2ban jail สำหรับ Stalwart** (587/993) เพิ่มจาก sshd ที่ cloud-init ทำไว้แล้ว

**เกณฑ์ผ่าน:**
1. ส่ง–รับกับ **Gmail + Outlook + Yahoo** ได้ (ทั้ง 3 เจ้า ไม่ใช่แค่ Gmail)
2. [mail-tester.com](https://www.mail-tester.com) ได้ **≥ 9/10**
3. ใช้เป็นเมลหลักจริง 2 สัปดาห์แล้ว**ไม่มีเมลหาย/ไม่มีเมลเข้าสแปม**
4. **ซ้อมกู้คืนจาก backup สำเร็จ 1 ครั้ง** (ดู §5.1 — snapshot ขณะเครื่องรันอาจกู้ไม่ได้)

### Phase 2 — โมดูล `mail` ใน PERPOS (โครง + provisioning)

**โมดูลใหม่** ใน [`lib/modules.ts`](apps/perpos/src/lib/modules.ts) — เป็น **shared** (ไม่ใส่ `forOrgSlugs`)
เพราะขายลูกค้าทั่วไป ต่างจาก `acc_firm`/`gov_procure` ที่ล็อก org เดียว

```ts
{
  key: "mail",
  label: "อีเมลบริษัท",
  href: "/mail",
  specific: true,
  match: (p) => { const s = p.split("/").filter(Boolean); return s.length >= 2 && s[1] === "mail"; },
  roles: [
    { key: "owner",  label: "ผู้ดูแลระบบเมล", canWrite: true },   // เพิ่ม/ลบกล่อง, ผูกโดเมน
    { key: "member", label: "ผู้ใช้",         canWrite: true },   // ใช้กล่องตัวเอง
    { key: "viewer", label: "ผู้ดูข้อมูล",     canWrite: false },
  ],
}
```

**ตาราง (migration `supabase/migrations/`)** — RLS ทุกตัวตาม convention:

| ตาราง | เก็บอะไร |
| ----- | -------- |
| `mail_domains` | โดเมนของแต่ละ org + สถานะยืนยัน (`pending`/`verified`/`failed`) + เวลาตรวจล่าสุด |
| `mail_dns_records` | record ที่ลูกค้าต้องไปตั้ง (type/host/value/ตรวจผ่านแล้วหรือยัง) — ทำหน้า "ตัวช่วยตั้ง DNS" |
| `mail_mailboxes` | กล่อง (org_id, domain_id, local_part, display_name, quota_bytes, สถานะ) |
| `mail_aliases` | alias / กลุ่มส่งต่อ |
| `mail_events` | bounce / complaint / delivery จาก SES (append-only) |
| `mail_usage_daily` | พื้นที่ใช้จริง + จำนวนเมลส่งต่อวัน ต่อ org (ป้อนหน้า billing) |

**ข้อผูกพันที่ห้ามพัง (invariant):**

1. **รหัสผ่านกล่องเมลไม่เก็บใน Supabase เด็ดขาด** — Stalwart hash เอง เราเก็บแค่ metadata
   ตอนสร้างกล่องให้แสดงรหัสชั่วคราวครั้งเดียวแล้วทิ้ง (เหมือน API key)
2. **API key ของ Stalwart Management API = service-role เท่านั้น** ห้ามหลุดถึง browser
   ทุกการ provision ผ่าน route handler ฝั่งเซิร์ฟเวอร์
3. **1 กล่องผูก 1 org เสมอ** — ทุก query ต้องกรอง `org_id` และผ่าน `getModuleRoleForCurrentUser`
   (**ห้ามใช้ admin service-role client กับข้อมูล per-org** ตามกฎใน AGENTS.md)
4. **`local_part@domain` unique ทั้งระบบ** — บังคับที่ DB ไม่ใช่แค่ตรวจในโค้ด
5. โดเมนที่ยังไม่ `verified` **ห้ามสร้างกล่องได้** (กันคนมาผูกโดเมนที่ไม่ใช่ของตัวเอง)

**API routes** (ห่อด้วย `withUsageContext` ทุกตัวตามกฎ metering):

### 5.1 🔴 backup ที่ "กู้ได้จริง" — snapshot ขณะเครื่องรันอาจใช้ไม่ได้

`backups = true` ของ Hetzner = **snapshot ทั้งดิสก์ขณะเครื่องกำลังรัน**
RocksDB มี memtable ค้างใน RAM + WAL ที่ยังไม่ flush → **snapshot อาจได้ฐานข้อมูลที่ inconsistent**
กู้มาแล้วเปิดไม่ขึ้น หรือแย่กว่า: เปิดขึ้นแต่ข้อมูลหายบางส่วนโดยไม่มีใครรู้

**ต้องทำเพิ่ม (Phase 1):**

1. **logical backup รายวัน** — export ข้อมูล Stalwart ออกเป็นไฟล์ (ไม่ใช่ snapshot ดิสก์)
   แล้วส่งขึ้น object storage คนละที่กับเครื่อง
2. **ซ้อมกู้จริงก่อนรับลูกค้ารายแรก** — สร้างเครื่องใหม่จาก backup แล้วเช็คว่าเมลครบ
   **นี่เป็นเกณฑ์ผ่าน Phase 1 ไม่ใช่ nice-to-have**
3. เก็บ backup **นอก Hetzner อย่างน้อย 1 ชุด** (R2/GCS) — กัน account โดนระงับแล้วเข้าถึงอะไรไม่ได้เลย

> "เมลลูกค้าหาย + backup กู้ไม่ได้" = จบธุรกิจในวันเดียว · นี่คือความเสี่ยงที่ร้ายแรงที่สุดในเอกสารนี้

### 5.2 ✅ ย้ายเมลเก่าเข้ามา — **ตัดสินใจแล้ว: ไม่ทำ (out of scope)**

**เราไม่ให้บริการย้ายเมลเก่า** ลูกค้าเริ่มกล่องใหม่ตั้งแต่วันที่เปิดใช้

#### ผลดี (มากกว่าที่คิด)

- **ข้อขัดแย้งเรื่องโควตา 1GB หายไปทั้งข้อ** — ไม่มีเมลเก่า 3–10GB มายัดกล่อง 1GB อีกต่อไป
  → 1GB เป็นขนาดที่สมเหตุผลสำหรับกล่องที่เริ่มจากศูนย์
- **ดิสก์โตช้าและคาดเดาได้** — วางแผนพื้นที่ง่ายขึ้นมาก
- **M0 เล็กลง** ไม่ต้องทำเครื่องมือย้าย + ไม่ต้องรับผิดชอบเวลาย้ายแล้วเมลหาย
  (การย้ายเมลเป็นงานที่พังบ่อยและโทษเราได้ง่ายที่สุด)

#### ⚠️ ผลกระทบที่ต้องรับรู้ — **ตลาดแคบลง**

ลูกค้าที่จะซื้อได้เหลือ 3 กลุ่ม:

1. **บริษัทเปิดใหม่ / โดเมนใหม่** — ไม่มีเมลเก่าอยู่แล้ว ✅ **กลุ่มเป้าหมายหลัก**
2. **บริษัทที่ยังใช้เมลฟรี** (Gmail ส่วนตัว, เมลของโฮสต์เว็บ) แล้วอยากมีเมลบริษัทจริง ✅
3. บริษัทที่ยอมทิ้งเมลเก่า / เก็บระบบเก่าไว้อ่านอย่างเดียว

**กลุ่มที่ขายไม่ได้:** บริษัทที่ใช้ Google Workspace / M365 อยู่แล้วและต้องการย้ายทั้งประวัติ
— **ซึ่งเป็นกลุ่มที่จ่ายเงินอยู่แล้วและมีงบ** · ยอมรับได้ในช่วงแรก แต่**รู้ไว้ว่ากำลังตัดตลาดส่วนนี้ทิ้ง**

#### 💡 สิ่งที่บอกลูกค้าแทน (ไม่ต้องเขียนโค้ดเลย)

"ไม่มีบริการย้าย" ≠ "ย้ายไม่ได้" — ลูกค้าย้ายเองได้ฟรีอยู่แล้ว **เราแค่ทำคู่มือ ไม่ต้องทำระบบ**:

| วิธี | ทำยังไง | เหมาะกับ |
| --- | -------- | -------- |
| **เปิดสองบัญชีคู่กัน** | ใส่ทั้งกล่องเก่าและใหม่ใน Outlook/Apple Mail · เมลใหม่เข้ากล่องใหม่ · เมลเก่ายังอ่านได้ที่เดิม | **ท่ามาตรฐานที่แนะนำ** — ง่ายสุด ไม่มีอะไรพัง |
| **ลากไฟล์ข้ามบัญชี** | เปิดสองบัญชีใน Thunderbird/Outlook แล้วลากโฟลเดอร์ที่อยากเก็บมาไว้กล่องใหม่ | ลูกค้าที่อยากเก็บเฉพาะเมลสำคัญ (ระวังโควตา) |
| **เก็บเป็นไฟล์** | ส่งออกเป็น .pst/.mbox เก็บไว้ในเครื่อง | เก็บตามกฎหมายอย่างเดียว ไม่ต้องอ่านบ่อย |

> **ทำหน้าคู่มือ 1 หน้าใน `/mail/settings` ก็พอ** — ตอบข้อโต้แย้ง "แล้วเมลเก่าล่ะ" ได้โดยไม่ต้องลงทุนอะไร
> · ถ้าวันหนึ่งเสียดีลใหญ่เพราะเรื่องนี้บ่อย ๆ ค่อยกลับมาทำเครื่องมือย้าย (imapsync) ทีหลังได้

### 5.3 ✅ DKIM — **เคาะแล้ว: ให้ SES เซ็นด้วย Easy DKIM** (แก้คำแนะนำเดิมที่ผิด)

> ⚠️ เอกสารรอบก่อนเสนอว่า "ให้ Stalwart เซ็น เพราะ TXT เดียว ลูกค้าตั้งง่ายกว่า" — **เหตุผลนั้นผิด**
> เพราะลืมไปว่า **SES บังคับให้ยืนยันโดเมนก่อนถึงจะส่งแทนได้อยู่ดี** ซึ่งกินระเบียน DNS ไปแล้ว
> ⇒ ให้ Stalwart เซ็น = ต้องตั้ง **ทั้ง** TXT ของ Stalwart **และ** ระเบียนยืนยันของ SES = **มากกว่า ไม่ใช่น้อยกว่า**

#### ข้อเท็จจริงที่ต้องรู้ก่อนตัดสินใจ

1. **SES เติมลายเซ็น `d=amazonses.com` ให้ทุกฉบับเสมอ** ไม่ว่าเราจะเซ็นเองหรือไม่
   — ลายเซ็นนั้น **ไม่ align กับโดเมนลูกค้า** จึงไม่ช่วยเรื่อง DMARC
2. **SES ไม่ลบลายเซ็นที่มีมาก่อน** (รองรับ manual signing อย่างเป็นทางการ) — ส่งผ่านได้จริง
3. **DMARC ผ่านถ้ามีลายเซ็นที่ align อย่างน้อย 1 อัน** — ลายเซ็นที่ fail ไม่ทำให้ DMARC ตก
4. **การยืนยันโดเมนใน SES กับการตั้ง DKIM คือระเบียนชุดเดียวกัน** — ทำ DKIM = ยืนยันโดเมนไปในตัว

#### เทียบ 3 ทาง

| | Stalwart เซ็น | **SES Easy DKIM** ✅ | SES BYODKIM |
| - | ------------- | -------------------- | ----------- |
| ระเบียนที่ลูกค้าต้องตั้ง | TXT 1 + **ระเบียนยืนยัน SES อีก** | **CNAME 3** (ยืนยันโดเมนในตัว) | TXT 1 (ยืนยันในตัว) |
| **หมุนกุญแจ** | Stalwart ทำเอง | ✅ **AWS ทำให้ ลูกค้าไม่ต้องแตะ DNS อีกเลย** | ❌ **เราต้องทำเอง = ขอลูกค้าทุกรายแก้ DNS ใหม่** |
| DMARC align | ✅ | ✅ | ✅ |
| ผูกกับ SES | ไม่ผูก | ผูก (ย้าย relay = ตั้ง DNS ใหม่ทุกราย) | ผูกน้อยกว่า |
| งานซัพพอร์ตระยะยาว | กลาง | **ต่ำสุด** | **สูงสุด** |

#### ✅ ตัดสินใจ: **Easy DKIM (CNAME 3 ระเบียน)**

**เหตุผลเดียวที่สำคัญที่สุด: การหมุนกุญแจ**
BYODKIM ประหยัดระเบียนตอนตั้งครั้งเดียว แต่แลกกับการที่ **เราต้องขอให้ลูกค้าทุกรายแก้ DNS ใหม่ทุกครั้งที่หมุนกุญแจ**
— ที่ 50 ลูกค้าคือฝันร้ายของทีมเล็กที่ไม่มี SLA · Easy DKIM = ตั้งครั้งเดียวจบตลอดกาล

3 ระเบียนไม่ใช่ปัญหา เพราะ**ตัวช่วยตั้ง DNS ของเรา generate + ปุ่มคัดลอก + ตรวจสอบสดให้อยู่แล้ว**
(§5.1 ของ [`MAIL_UI_SPEC.md`](MAIL_UI_SPEC.md)) — ลูกค้าเห็นเป็นการ์ดให้กดคัดลอกทีละอัน ไม่ได้พิมพ์เอง

#### สิ่งที่ต้องทำตามการตัดสินใจนี้

- **ปิด DKIM signing ของ Stalwart สำหรับโดเมนลูกค้า** — ไม่งั้นได้ลายเซ็นซ้อนที่ไม่มีประโยชน์
  (เก็บความสามารถไว้ ถ้าวันหนึ่งขอปลดพอร์ต 25 แล้วส่งตรงเองโดยไม่ผ่าน SES ค่อยเปิด)
- **ท่อ provisioning อัตโนมัติ** — ตอนลูกค้าเพิ่มโดเมน:
  1. เรียก SES `CreateEmailIdentity` → ได้ DKIM token 3 ตัว
  2. เขียนลง `mail_dns_records` → ตัวช่วยตั้ง DNS แสดงให้ลูกค้าคัดลอก
  3. poll `GetEmailIdentity` ทุก 30 วิ → พอ `verified` ปลดล็อกให้สร้างกล่องได้
- **SPF `include:amazonses.com`**: ⚠️ **ระเบียนนี้ไม่ได้ทำงานอย่างที่หลายคนคิด** —
  SES ใช้ MAIL FROM ของตัวเอง (`*.amazonses.com`) ดังนั้น SPF ถูกตรวจกับระเบียนของ AWS ไม่ใช่ของลูกค้า
  · **สิ่งที่ทำให้ DMARC ผ่านจริงคือ DKIM** · ยังใส่ไว้ได้ (ไม่เสียหาย + จำเป็นถ้าอนาคตตั้ง custom MAIL FROM)
  แต่**อย่าเข้าใจผิดว่าตัดออกแล้วเมลจะพัง หรือใส่แล้วจะแก้ปัญหา deliverability ได้**
- (ทำทีหลังได้) **custom MAIL FROM ต่อโดเมน** → ได้ SPF align ด้วย แต่ +2 ระเบียน/ลูกค้า ·
  ทำเมื่อเจอปัญหา deliverability จริง ไม่ใช่ทำไว้ก่อน

#### ✅ เคาะแล้ว: **ไม่มี SLA — ขายแบบ best effort**

ถูกต้องแล้วสำหรับช่วงนี้ (ทีมเล็ก เครื่องตัวเดียว ยังไม่มี backup MX) **แต่ "ไม่มี SLA" ไม่ได้แปลว่าไม่ต้องทำอะไร**:

| ------ | ----- |

| **ประกาศล่วงหน้าเมื่อจะปิดปรับปรุง** | ล่มโดยไม่บอก = เสียความเชื่อใจมากกว่าตัวการล่มเอง |
| **ทบทวนเมื่อถึง ~50 กล่อง** | ลูกค้าองค์กรจะเริ่มขอ SLA เป็นเงื่อนไขจัดซื้อ — ถึงตอนนั้นต้องมี backup MX ก่อน (Phase 6) |

### 5.5 🟡 สแปมขาเข้า + false positive

- Stalwart Community มี spam filter เชิงสถิติ — **ต้องสอนมัน** (ช่วงแรกจะปล่อยสแปมผ่านเยอะ)
- **ยังไม่มี antivirus ในแผน** — ธุรกิจไทยเจอไฟล์แนบอันตรายบ่อย · พิจารณา ClamAV (กิน RAM ~1GB
  → **`cpx11` 2GB อาจไม่พอ ต้องขยับเป็น `cpx21`**)
- **false positive อันตรายกว่าสแปมหลุด** — "ใบสั่งซื้อลูกค้าหายไปในสแปม" = เรื่องใหญ่
  → ต้องมีโฟลเดอร์สแปมที่ลูกค้าเห็นได้ + กู้กลับได้ + **ห้ามลบอัตโนมัติเร็วเกิน 30 วัน**

### 5.6 🟡 ฟีเจอร์ที่ลูกค้าไทยถามแน่ ๆ แต่ยังไม่มีในแผน

| ขอ | สถานะ |
| --- | ----- |
| `info@` ที่หลายคนเข้าถึงร่วมกัน (shared mailbox) | Stalwart รองรับ แต่ **UI ยังไม่ได้ออกแบบ** |
| catch-all (`*@domain` เข้ากล่องเดียว) | รองรับ · ต้องเตือนว่าจะดูดสแปมมหาศาล |
| กลุ่มส่งต่อ (`sales@` → 5 คน) | อยู่ใน `mail_aliases` แล้ว ✅ |
| ลายเซ็นบริษัทแบบบังคับทั้ง org | **ยังไม่มีในแผน** |
| ตอบอัตโนมัติ (ลาพักร้อน) | อยู่ใน `/mail/settings` แล้ว ✅ |
| เก็บสำเนาเมลทุกฉบับตามกฎหมาย (journaling) | **ยังไม่มี** — ลูกค้าที่มี compliance จะถาม |

### 5.7 🟡 อัปเกรด Stalwart

ไบนารีเดียวก็จริง แต่การอัปเกรดมี schema migration ของ RocksDB ได้ —
**ต้องมีขั้นตอน: backup → อัปเกรดบนเครื่องทดสอบ → ค่อยทำ production**
· อย่าอัปเกรดตรงบน production เพราะ "มันเป็นแค่ไบนารีเดียว"
· Oracle Always Free ที่จะทำ backup MX ใน Phase 6 **ใช้เป็นเครื่องทดสอบอัปเกรดได้ด้วย**

## 6. DNS ที่ลูกค้าแต่ละรายต้องตั้ง

หน้า "ตัวช่วยตั้ง DNS" ต้องปั่น record ชุดนี้ + **ปุ่มตรวจสอบว่าตั้งถูกยัง** (ห้ามให้ลูกค้าเดาเอง)

| Type | Host | Value | ทำไม |
| ---- | ---- | ----- | ---- |
| MX | `@` | `mail.perpos.ai` (priority 10) | รับเมลเข้า |
| TXT | `@` | `v=spf1 include:amazonses.com ~all` | ⚠️ **ไม่ใช่ตัวที่ทำให้ DMARC ผ่าน** — SES ใช้ MAIL FROM ของตัวเอง · ใส่ไว้เผื่ออนาคต (§5.3) |
| **CNAME ×3** | `xxx._domainkey` | (SES Easy DKIM — API สร้างให้อัตโนมัติ) | ⭐ **ตัวที่ทำให้ DMARC ผ่านจริง** + ยืนยันโดเมนใน SES ไปในตัว · AWS หมุนกุญแจให้ ลูกค้าไม่ต้องแตะอีก |
| TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:dmarc@perpos.ai` | เริ่มที่ `p=none` เก็บสถิติ 2–4 สัปดาห์ ค่อยขยับ `quarantine` |
| CNAME | `autodiscover` | `mail.perpos.ai` | Outlook ตั้งค่าเอง |
| SRV | `_autodiscover._tcp` | `mail.perpos.ai:443` | Outlook |
| CNAME | `autoconfig` | `mail.perpos.ai` | Thunderbird / Apple Mail |

> **ห้ามให้กล่องเมลใช้งานได้ก่อน DNS ผ่านครบ** — ปล่อยผ่านแล้วลูกค้าจะส่งเมลออกไปเข้าถังสแปม
> แล้วโทษเรา งานซัพพอร์ตจะท่วม

## 7. กฎหมาย / PDPA — เรื่องที่ต้องทำ ไม่ใช่ทางเลือก

- **เนื้อหาอีเมลของลูกค้า = ข้อมูลส่วนบุคคลที่อ่อนไหวที่สุดเท่าที่ PERPOS เคยเก็บ** — หนักกว่าเอกสารบัญชี
- ต้องอัปเดต [นโยบายความเป็นส่วนตัว](apps/landing-astro/src/lib/legal.ts): เก็บอะไร, เก็บที่ไหน
  (**Hetzner สิงคโปร์** — ผู้ให้บริการเยอรมัน ศูนย์ข้อมูลสิงคโปร์), เก็บนานแค่ไหน, ลบอย่างไรเมื่อเลิกใช้
- ต้องมี **ข้อตกลงประมวลผลข้อมูล (DPA)** กับลูกค้าแต่ละราย — เราเป็น "ผู้ประมวลผล" ลูกค้าเป็น "ผู้ควบคุม"
  · และเราต้องมี DPA **จาก Hetzner และ AWS** ด้วย (ทั้งคู่เป็นผู้ประมวลผลช่วง) — ทั้งสองเจ้ามีให้ดาวน์โหลด
- **ต้องมีทางส่งออกข้อมูลให้ลูกค้าตอนเลิกใช้** (export .mbox/.eml ทั้ง org) — PDPA บังคับ และเป็น
  เงื่อนไขที่ลูกค้าองค์กรถามก่อนเซ็นเสมอ ("ถ้าเลิกใช้ เอาเมลออกยังไง")
- **ผู้ดูแลระบบ (รวมเราเอง) ต้องอ่านเมลลูกค้าไม่ได้** — ออกแบบให้ admin เห็นแค่ metadata
  ถ้าจำเป็นต้องเข้าถึงเพื่อแก้ปัญหา ต้องมี audit log + ลูกค้ายินยอมเป็นครั้ง ๆ
- ⚠️ **ห้ามส่งเนื้อหาเมลเข้า AI ทุกกรณีจนกว่าจะแก้นโยบายก่อน** — AGENTS.md ระบุว่าเรารับรองกับ Google
  ไว้เรื่อง Limited Use ถ้าจะทำ "AI สรุปเมล" ต้องอัปเดตนโยบาย §7 และแจ้ง Google **ก่อน** เขียนโค้ด

1. **ตัวเลขเป็นค่าประมาณ — ยืนยันกับหน้าราคา Hetzner ก่อนตั้งงบ** (สิงคโปร์แพงกว่าราคายุโรปที่ประกาศ)

### กลยุทธ์ B — ไม่รันเซิร์ฟเวอร์เลย ซื้อของเจ้าอื่นมาขายต่อ

| Zoho Mail Lite | $1/user/เดือน | 5GB/คน | ฿34 × 5 = ฿170 |

**ถูกกว่ารันเองสิบเท่า** — แต่**เปลี่ยนโมเดลธุรกิจ** จาก "เจ้าของบริการ" เป็น "นายหน้า" และมี 5 ข้อเสียที่ต้องรู้:

1. **ไม่มี JMAP** → webmail ที่จะเขียนใน Next.js ต้องต่อ IMAP แทน (ต้องมี bridge IMAP→HTTP วางบน Cloud Run)
2. **ไม่มี isolation จริง** → ลูกค้าทุกรายอยู่บัญชีเดียวกัน · **ลูกค้ารายหนึ่งส่งสแปม = ทุกรายโดนหางเลข** และเราแก้ไม่ได้
3. **ชื่อเสียง IP เป็นของเขา ไม่ใช่ของเรา** — เขาโดน blacklist เมื่อไหร่ ลูกค้าเราเดือดร้อนทันทีและเราทำอะไรไม่ได้เลย
4. **fair use ≠ ใบอนุญาตทำธุรกิจ** — Purelymail "$10 ไม่จำกัด" ตั้งอยู่บนการใช้แบบส่วนตัว
   เอาไปขายต่อเชิงพาณิชย์เสี่ยงโดนคิดเพิ่ม/ปิดบัญชี · **ถ้าจะใช้ทางนี้ให้เลือก MXroute ที่ประกาศชัดว่ารับนายหน้า**
5. **ไม่มี moat** — ลูกค้าไปซื้อตรงกับเขาเองได้ ราคาถูกกว่าเราอีก

## 9. ความเสี่ยงที่ต้องรับรู้ก่อนตัดสินใจ

| ความเสี่ยง | ระดับ | รับมือ |
| ---------- | ----- | ------ |
| พอร์ตขาออกไป SES ถูกบล็อก | **ต่ำ** | Hetzner ไม่บล็อก 587 · ยืนยันใน Phase 0 ข้อ 3 · ขอปลด 25 ได้หลังบิลแรก |
| เครื่องตัวเดียว = SPOF | **สูง** | Phase 6 เพิ่ม backup MX — ระหว่างนี้ต้องบอกลูกค้าตรง ๆ ว่ายังไม่มี SLA |
| ลูกค้ารายหนึ่งส่งสแปม | กลาง | SES Tenants แยกชื่อเสียง + AUP + ตรวจลูกค้าก่อนเปิด |
| เมลตกถังสแปมตอนเริ่มใหม่ | กลาง | warm-up ค่อย ๆ เพิ่ม · DMARC เริ่ม `p=none` · เฝ้า Google Postmaster Tools |
| ลูกค้าตั้ง DNS ผิด | กลาง | บังคับ verify ก่อนใช้ + ปุ่มตรวจสอบในหน้าเว็บ |
| งาน webmail บานปลาย | **สูง** | ขายตั้งแต่ Phase 2 (ใช้ Outlook ได้) — webmail เป็นของแถมที่ค่อยทยอยออก |
| ข้อมูลลูกค้ารั่วข้าม org | **สูงมาก** | invariant §Phase 2 + เทสคุม + ห้าม service-role กับข้อมูล per-org |
| **backup กู้ไม่ได้จริง** | **สูงมาก** | §5.1 — logical backup + ซ้อมกู้เป็นเกณฑ์ผ่าน Phase 1 |
| **ตลาดแคบเพราะไม่รับย้ายเมลเก่า** | กลาง | §5.2 — จงใจ · เจาะบริษัทเปิดใหม่/ที่ยังใช้เมลฟรี · มีคู่มือย้ายเองแทน |
| **ต้นทุนคน (ซัพพอร์ต) เกินที่คิด** | **สูง** | §5.4 — ขายแบบไม่มี SLA ก่อน + ตั้งราคาเผื่อค่าแรง |
| ดิสก์เต็มเร็วกว่าที่คิด | กลาง | §3 — เตือนที่ 70% · Volume ขยายได้ไม่ต้องดับเครื่อง |
