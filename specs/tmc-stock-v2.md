## 1. ปัญหาของโครงเดิม

| เดิม                                            | พัง/ทำไม่ได้                                                                                           |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `tmc_stock_items.current_qty` ตัวเดียวต่อสินค้า | ผ้าอยู่ได้หลายที่พร้อมกัน (คลังกลาง / ในห้อง / ร้านซัก) — เลขเดียวตอบไม่ได้ว่า "ผ้าสะอาดพอไหม"         |
| `movement_type` = `in`/`out` เฉย ๆ              | "เบิกไป TMC3" กับ "ส่งซัก" กับ "ผ้าขาดทิ้ง" ต่างกันสิ้นเชิง แต่ถูกบันทึกเหมือนกัน                      |

| ไม่ผูกกับการเข้าพัก                             | คิดต้นทุนของใช้ต่อคืน (CPOR) ไม่ได้ ทั้งที่ `tmc_stays` มีข้อมูลครบ                                    |

## 2. แกนของระบบใหม่ — 3 เรื่อง

### 2.1 แบ่งของเป็น 2 ชั้น (class → group)

```
stock_class = 'consumable'   ใช้แล้วหมดไป — ตัดออกจากระบบเมื่อใช้
   ├─ group 'amenity'      แปรงสีฟัน หมวกคลุมผม สลิปเปอร์ คัตเติลบัด ทิชชู
   ├─ group 'fnb'          กาแฟ อาหารเช้า ไวน์ เครื่องดื่ม
   ├─ group 'cleaning'     เป็ดโปร แฟบ ถุงขยะ น้ำยาเช็ดกระจก ไบโอเมท
   └─ group 'maintenance'  หลอดไฟ สกรู อะไหล่ (ของซ่อมบำรุงที่ใช้แล้วหมด)

stock_class = 'reusable'     ใช้ซ้ำ — ไม่หายจากทรัพย์สิน แค่ย้ายที่
   ├─ group 'linen'        ผ้าปูที่นอน ปลอกผ้านวม ผ้าเช็ดตัว ผ้าเช็ดเท้า ผ้าคลุมโต๊ะ
   ├─ group 'bedding'      ไส้ผ้านวม หมอน Topper รองกันเปื้อน  (ใช้ซ้ำแต่ไม่ส่งซักทุกรอบ)
   └─ group 'equipment'    เครื่องมือ/ทรัพย์สินย่อยที่ยืม-คืน
```

กติกาที่ต่างกันชัดเจน:

|                   | consumable                         | reusable                                               |
| ----------------- | ---------------------------------- | ------------------------------------------------------ |
| เบิกไปห้อง        | = ใช้ไปแล้ว ตัดจบ (ไม่นับในห้อง)   | = **ย้ายที่** ยังอยู่ในทรัพย์สิน                       |
| หายจากระบบเมื่อ   | ใช้ / หมดอายุ / เสียหาย            | ทิ้ง (ผ้าเสีย) / สูญหาย เท่านั้น — **ต้องระบุเหตุผล**  |
| ตัวเลขที่ผู้ใช้ดู | "คงเหลือรวม" + "ถึงจุดสั่งซื้อ"    | "อยู่ที่ไหนบ้าง" (คลังกลาง / ห้อง / ร้านซัก) + "พอไหม" |
| ต้นทุน            | ต้นทุนเฉลี่ย → เข้าค่าใช้จ่ายทันที | ต้นทุนซื้อ = ทรัพย์สิน · **ค่าซัก = ค่าใช้จ่ายต่อรอบ** |

### 2.2 ทุกอย่างเป็นการ "ย้ายจากที่หนึ่งไปอีกที่หนึ่ง"

หัวใจของโครงใหม่: **1 movement = `from_location` → `to_location`** (ฝั่งไหนเป็น `NULL` = นอกระบบ)

```
ซื้อเข้า          NULL          → คลังกลาง
เบิกไปห้อง        คลังกลาง       → TMC3-4
ส่งซัก            TMC3-4        → ร้านซัก ก.
รับคืนผ้าซัก      ร้านซัก ก.     → ห้องผ้าสะอาด
ผ้าเสีย/ทิ้ง       ห้องผ้าสะอาด   → NULL      (reason = 'damaged')
สูญหาย            TMC5          → NULL      (reason = 'lost', ผูก stay_id → หักประกัน)
ใช้หมดไป          TMC1          → NULL      (reason = 'consumed')  ← consumable เท่านั้น
```

**ยอดคงเหลือไม่ถูกเก็บมือ** — `balance(item, location) = Σ(เข้า) − Σ(ออก)` เก็บใน `tmc_stock_balances` ที่ maintained โดย trigger เท่านั้น (invariant เดียวกับ `just_me`: ห้ามเขียนยอดตรง ๆ)

### 2.3 ผ้า = ต้องมี "รอบซัก" ไม่ใช่แค่ movement

ไฟล์จริงบันทึก "รับคืนผ้าซัก 14 ผืน ราคา 10 บาท/ผืน" → ต้องเป็นเอกสาร 1 ใบ ที่ **ส่งไป vs กลับมา จับคู่กันได้** ไม่งั้นผ้าหายแล้วไม่มีใครรู้

## 3. Schema ที่เสนอ

### ตารางใหม่

```sql
-- 3.1 จุดเก็บของ (แทนคอลัมน์ property_code เดี่ยว ๆ)
tmc_stock_locations (
  id, org_id,
  code            text,      -- 'WH', 'TMC1', 'LAUNDRY-A', 'LINEN', 'KITCHEN', 'STORE-A'
  name            text,
  kind            text,      -- warehouse | property | laundry | linen_room | kitchen | store
  property_id     uuid null, -- ผูก tmc_properties เมื่อ kind='property'
  is_external     bool,      -- ร้านซัก = true (ของอยู่นอกบ้านเรา แต่ยังเป็นของเรา)
  is_active, sort_order
)
-- seed: คลังกลาง · TMC1,2,3-4,5,6,7 · ส่วนกลาง · ห้องผ้าสะอาด · ผ้าเปื้อนรอส่ง · ร้านซัก(N ร้าน)
--       + สโตร A / B / C / VELA (ถ้าเลือกเก็บของก่อสร้างไว้ที่นี่ — ดู §7)

-- 3.2 ยอดคงเหลือ (derived, trigger เท่านั้น)
tmc_stock_balances (org_id, item_id, location_id, qty, updated_at, PK(item_id,location_id))

-- 3.3 par level: แต่ละที่ "ควรมี" เท่าไร
tmc_stock_par_levels (org_id, item_id, location_id, par_qty)
-- เช่น TMC3-4 ควรมีผ้าปู 6ฟุต 2 ผืน, ผ้าเช็ดตัว 4 ผืน → ระบบบอกว่า "ต้องเติมอีกกี่ผืน"

-- 3.4 ชุดของต่อการเข้าพัก (BOM)
tmc_room_kits       (id, org_id, name, property_code null, guests_from, guests_to)
tmc_room_kit_lines  (kit_id, item_id, qty, per_night bool)
-- กดปุ่มเดียวตอนเช็คเอาต์ = เบิกทั้งชุด (ผ้าชุดใหม่ + amenity) ผูก stay_id ให้อัตโนมัติ

-- 3.5 รอบซัก
tmc_laundry_batches (
  id, org_id, vendor_name, ref_no,
  sent_at date, returned_at date null,
  status text,         -- draft | sent | partial | closed
  total_sent int, total_returned int, total_damaged int, total_missing int,
  laundry_cost numeric,          -- ค่าซักรวม → สร้าง tmc_finance_entries เมื่อปิดรอบ
  finance_entry_id uuid null,
  created_by, created_at
)
tmc_laundry_batch_lines (batch_id, item_id, qty_sent, qty_returned, qty_damaged, unit_price)
tmc_laundry_prices      (org_id, item_id, price_per_piece)   -- จากไฟล์: ผ้าปู 18 / ปลอกผ้านวม 35 / ผ้าเช็ดตัว 10 / ผ้าเย็น 5

-- 3.6 นับสต๊อกจริง (cycle count) — ยืมแพตเทิร์นจาก just_me_stock_count
tmc_stock_counts      (id, org_id, location_id, count_date, status draft|closed, note, created_by)
tmc_stock_count_lines (count_id, item_id, system_qty, counted_qty, diff)
-- ปิดรอบ → gen movement 'adjust' อัตโนมัติให้ยอดตรงของจริง (ห้ามแก้ balance ตรง ๆ)
```

### แก้ตารางเดิม

```sql
alter table tmc_stock_items add
  stock_class     text not null default 'consumable',  -- consumable | reusable
  item_group      text,                                -- amenity|fnb|cleaning|maintenance|linen|bedding|equipment
  sku             text,
  pack_size       numeric default 1,      -- 1 ห่อ = 20 ชิ้น → ซื้อเป็นห่อ เบิกเป็นชิ้น
  purchase_unit   text,                   -- หน่วยซื้อ (ห่อ/ลัง) ต่างจาก unit ที่ใช้จริง
  reorder_point   numeric,                -- ใช้แทน/เสริม min_quantity
  avg_cost        numeric,                -- ต้นทุนเฉลี่ยเคลื่อนที่
  consumes_on_issue bool default true,    -- consumable: เบิก=ใช้เลย ไม่นับในห้อง
  track_expiry    bool default false,     -- F&B: เตือนใกล้หมดอายุ
  is_chargeable   bool default false,     -- ขายแขกได้ (มินิบาร์)
  sale_price      numeric,
  default_location_id uuid;              -- "บ้าน" ของสินค้าชิ้นนี้ — ต้นทาง/ปลายทางเมื่อ movement ไม่ระบุ
-- current_qty: คงไว้เป็น cache ของยอดรวมทุก location (trigger เขียน) — ห้ามใช้ตัดสินใจเรื่องผ้า

alter table tmc_stock_movements add
  from_location_id uuid null references tmc_stock_locations,
  to_location_id   uuid null references tmc_stock_locations,
  reason           text,           -- consumed | damaged | lost | correction | guest_charge
  stay_id          uuid null references tmc_stays,
  batch_id         uuid null references tmc_laundry_batches,
  count_id         uuid null references tmc_stock_counts,
  expiry_date      date null,
  ref_movement_id  uuid null;      -- คู่กลับรายการ (reversal) — ห้ามลบ movement
-- movement_type ใหม่: receive | issue | transfer | send_wash | return_wash |
--                      consume | retire | lost | adjust | sale
```

### Invariant ที่ห้ามพัง

1. **`tmc_stock_balances` เขียนจาก trigger ของ `tmc_stock_movements` ทางเดียว** — ไม่มี API ไหนอัปเดตยอดตรง ๆ
2. **ห้ามลบ/แก้ movement** — แก้ผิดต้องออกรายการกลับ (`ref_movement_id`) เสมอ (ผ้าเป็นทรัพย์สิน ต้องตรวจสอบย้อนได้)
3. **reusable ออกจากระบบได้เฉพาะ `retire` / `lost`** และต้องมี `reason` + ผู้บันทึก
4. **รอบซักปิดได้เมื่อ `sent = returned + damaged + missing`** — ส่วนต่างต้องถูกอธิบาย ไม่ใช่หายเงียบ
5. เงิน: ค่าซัก + ค่าซื้อของ → `tmc_finance_entries` ผ่าน RPC atomic ตัวเดียว (แพตเทิร์นเดียวกับ `tmc_purchase_stock`) · RPC ทุกตัว `revoke from public, anon, authenticated`
6. ไม่มีข้อมูล = `NULL` ไม่ใช่ 0 (par ที่ยังไม่ตั้ง ≠ par 0)

## 4.5 เบิกของแบบ preset — "ชุดของประจำห้อง"

> เป้าหมาย: แม่บ้านไม่ต้องจำว่าห้องหนึ่งใช้อะไรบ้างกี่ชิ้น และไม่ต้องคีย์ทีละบรรทัด
> **preset = ค่าตั้งต้น ไม่ใช่กฎเหล็ก** — แก้จำนวนก่อนยืนยันได้เสมอ และเพิ่มรายการนอกชุดได้

### แนวคิด

```
เลือกหลัง (TMC3-4) → เลือกชุด (เซ็ตห้องหลังเช็คเอาต์) → ตารางขึ้นมาพร้อมจำนวน
   → แก้จำนวน / เพิ่มรายการ / เอาออก ได้ตรงนั้น → กดยืนยัน
   → ระบบสร้าง "ใบเบิก" 1 ใบ + movement ทุกบรรทัด ผูก stay_id ให้อัตโนมัติ
```

บรรทัดในชุดเดียวกันปฏิบัติต่างกันตาม `stock_class` ของสินค้า **โดยที่คนเบิกไม่ต้องรู้**:

- consumable (แปรงสีฟัน สลิปเปอร์ กาแฟ) → `คลังกลาง → NULL` = ใช้ไปแล้ว ตัดจบ
- reusable (ผ้าปู ผ้าเช็ดตัว) → `ห้องผ้าสะอาด → TMC3-4` = ย้ายที่ ยังเป็นทรัพย์สินเรา

### ตาราง

```sql
tmc_stock_presets (
  id, org_id,
  name           text,        -- 'เซ็ตห้องหลังเช็คเอาต์', 'เติมของระหว่างพัก', 'ของต้อนรับ'
  preset_kind    text,        -- checkout | daily | welcome | custom

### กติกา

1. **แก้ชุดได้เอง** (owner/admin/team_lead): เพิ่มรายการ · แก้จำนวน · ปิดชั่วคราว · คัดลอกชุดไปหลังอื่น — ไม่ต้องรอ dev
2. **preset แก้ได้ แต่ประวัติต้องไม่เปลี่ยน** → `preset_snapshot` เก็บชุด ณ วันที่เบิก
3. **ตอนเบิกจริงแก้ได้เสมอ** — แก้จำนวน/เอาบรรทัดออก/เพิ่มรายการนอกชุด (ของที่เพิ่มเข้ามาไม่ถูกเขียนกลับเข้า preset อัตโนมัติ)
4. **ของไม่พอ** → เตือนตรงบรรทัดนั้น ให้เลือก "เบิกเท่าที่มี" หรือ "ข้ามบรรทัดนี้" · **reusable ห้ามติดลบเด็ดขาด**
5. **ยกเลิกใบเบิก** = ออก movement กลับทั้งชุด (`ref_movement_id`) ไม่ใช่ลบ
6. **RPC เดียว `tmc_stock_issue_preset()`** — atomic ทั้งใบ (ครึ่งใบไม่ได้)
7. `qty_basis` คูณจากข้อมูล stay จริง (`group_size`, `nights`) — ถ้าเบิกโดยไม่ผูก stay ให้คนกรอกตัวคูณเอง

**ต้องได้จากลูกค้า** — ร้านซักกี่เจ้า, คิดต่อผืนหรือต่อกิโล, ราคาต่อผืนปัจจุบัน

### P5 — ทำให้ระบบ "บอกเราเอง": par + พยากรณ์ผ้า + ใบเติมของ

**ทำอะไร**

- migration: `tmc_stock_par_levels`
- `lib/tmc/stock-forecast.ts` — **สูตรทั้งหมดอยู่ไฟล์เดียว** (แพตเทิร์นเดียวกับ `lib/just-me/project-metrics.ts`): ความต้องการผ้า 7/14 วันจาก `tmc_stays` × **preset ของ P3** เทียบ `สะอาดคงเหลือ + ที่จะกลับจากร้านซัก` · มี unit test
- ใบเติมของอัตโนมัติ: ต่ำกว่า `reorder_point` หรือต่ำกว่า par ของแต่ละหลัง → ร่างรายการซื้อ ต่อเข้า `tmc_purchase_stock`
- ภาพรวมเพิ่มการ์ด **"ผ้าพอถึงวันที่ …"**

**เสร็จเมื่อ** — เปิดหน้าภาพรวมแล้วตอบได้ทันทีว่าผ้าพอถึงเมื่อไร และมีรายการ "ต้องเติมวันนี้" ที่กดสั่งซื้อต่อได้

**เสี่ยง** กลาง — ตัวเลขผิดแล้วคนเชื่อผิด → สูตรต้องอยู่ที่เดียว + เทส · ไม่มีข้อมูล = `NULL` ไม่ใช่ 0

**ต้องได้จากลูกค้า** — par level ต่อหลัง (ผ้าแต่ละอย่างหลังละกี่ผืน) ← ถ้ายังไม่มีตัวเลขนี้ เฟสนี้ทำไม่ได้ · (ส่วน "หนึ่งห้องใช้อะไรบ้าง" ได้จาก preset ใน P3 แล้ว)

---

### P6 — ปิดรูรั่ว: นับสต๊อก + ผูกกับการเข้าพัก

**ทำอะไร**

- migration: `tmc_stock_counts` / `_lines` (ยืมแพตเทิร์น `just_me_stock_count`) · RPC ปิดรอบนับ → gen movement `adjust`
- หน้า **นับสต๊อก** (นับต่อจุดเก็บ, ผลต่าง, ปิดรอบ) + รายงาน "หายเดือนนี้กี่ผืน กี่บาท"
- ของหาย/เสียจากแขก → `lost` ผูก `stay_id` → เสนอหักจาก `deposit_received` (ปิดวงจร `tmc_stays.damaged_items` ที่ตอนนี้เป็นแค่ข้อความ)
- มินิบาร์: `is_chargeable` + `sale_price` → ตัดสต๊อก + บวกเข้า `food_amount`/`drink_amount` ของ stay
- F&B: `track_expiry` + วันหมดอายุตอนรับเข้า + เตือนใกล้หมด (FEFO)
- **CPOR** — ต้นทุนของใช้ต่อคืน (amenity + ค่าซัก + F&B) ÷ คืนที่ขาย แยกรายหลัง → ต่อเข้าหน้า `tmc/costs` เดิม

**เสร็จเมื่อ** — ปิดรอบนับแล้วยอดตรงของจริงโดยไม่มีใครแก้ยอดมือ · ตอบได้ว่าหลังไหนกินของเปลืองที่สุด

**เสี่ยง** กลาง — แตะเงินประกันของแขก (ต้องเป็น "เสนอให้คนกดยืนยัน" ไม่ใช่หักอัตโนมัติ)

### P7 — ยกไปหน้างาน: มือถือ + LINE + BI

**ทำอะไร**

- ต่อ `/api/tmc/mobile`: **เบิกชุด preset จากมือถือ** (เลือกหลัง → ชุด → ยืนยัน) / ส่งซัก / รับคืน / นับสต๊อก — ใช้ preset ชุดเดียวกับเว็บ ไม่ต้องพิมพ์
- ต่อยอด preset: ถ้าคนแก้จำนวนบรรทัดเดิมซ้ำ ๆ → เสนอ "อัปเดตชุดเป็นค่าใหม่ไหม"
- LINE แจ้งเตือน (Flex ตาม `docs/line-flex-card-guide.md`): ถึงจุดสั่งซื้อ · **ผ้าไม่พอสำหรับจองพรุ่งนี้** · รอบซักค้างเกิน 3 วัน · ผลต่างนับสต๊อกเกินเกณฑ์ — ยิงจาก scheduler tier ที่มีอยู่
- BI metrics scope `tmc`: มูลค่าสต๊อกคงเหลือ · ค่าซักต่อคืน · อัตราผ้าเสีย/เดือน · CPOR (ต่อยอด 12 metric draft เดิม)

**เสร็จเมื่อ** — คนหน้างานไม่ต้องเปิดคอมเพื่อบันทึกของ และเจ้าของรู้ปัญหาก่อนจะเป็นปัญหา

**เสี่ยง** ต่ำ — ต่อของที่มีอยู่แล้วทั้งหมด

```
P1 ──> P2 ──> P3 (preset) ──┬──> P4 (ซัก) ──> P5 (พยากรณ์) ──┬──> P7
                            └──────────────> P6 (นับ/stay) ──┘

- **คุ้มที่สุดต่อเจ้าของ** = ถึง P5 → ระบบเตือนเราเอง แทนที่จะรอเราไปเปิดดู
